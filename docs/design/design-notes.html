Project midna · design concepts · Oct 3, 2026

A terminal that agents run and you supervise when you choose

Midna replaces Saggar with a Rust terminal where projects hold terminals, a background daemon tracks every change, and every setting, window and tab can be driven through one API. People step in only where they've asked to approve.

Layout concepts

Four ways to arrange a project's terminals

Every concept uses the same objects: project → terminal (tab) → split. Each terminal has one of five states: working, needs you, done, unseen, failed and idle. The concepts differ only in how much of that they show at once, so they can coexist as views and you don't have to pick one.

This is Saggar's project menu turned into a permanent sidebar of vertical tabs, along the lines of cmux. Each row shows enough context (branch, ports, last message) that you rarely need to open it. Why it works

  • Answers "which terminal needs me?" at a glance and across every project.
  • An approval is a structured request showing the command, the rule that triggered it and how long the answer applies. You don't have to switch to the terminal and press y.
  • Three landmark regions (sidebar, terminal, inbox) give screen readers clear stops. F6 moves between them.

Risks

  • The most chrome of the four. The sidebar and inbox both need to collapse (⌘\, ⌘I).
  • With 30+ terminals the sidebar gets long. Projects with nothing to report collapse into "+ N quiet projects".

Why it works

  • Covers the window actions you asked for: bring to front, keep on top, snap to a side, open and close windows.
  • Midna can pin its own windows on top using a public macOS API, so it's reliable.

Limits

  • macOS doesn't let one app keep another app's window on top. Moving, resizing and raising other apps' windows works once you grant Accessibility permission. "Keep on top" for other apps can only re-raise the window after it loses focus.

Recommendation: one layout with three zoom levels

Make Command Deck the home view, with Overview (⌘O) and Focus (⌘⇧↩) as zoomed-out and zoomed-in versions of it, and Satellites as something any terminal can do. Every view reads the same state from the daemon, so an agent that renames a tab or raises a flag changes all of them at once.

Dictation · Kass

Make the prompt a real text field

When Kass dictates into another app, it first asks macOS for the focused text field. Through that, it reads the words before the cursor (so "no, actually…" and voice edits work), inserts text directly and checks that the text actually landed. Every terminal fails that check. They expose their output history as the "text field", but your typing goes to the shell, not to that field. So Kass marks every terminal, Saggar included, as paste-only (CLIPBOARD_ONLY_BUNDLES in text_insert.rs). In a terminal you get no context, no voice edits, no rewriting a selection with Command Mode, and no confirmation that the text arrived.

Midna knows where the input is, so it can expose that input as an ordinary text field.

Agent terminals: a composer

Claude Code and Codex draw their own input box out of terminal characters, so macOS can't see it. Midna puts a native text field (a real NSTextView, not a GPUI drawing) under every agent terminal. Kass, the Mac's own dictation, spellcheck and the international input methods all treat it like any other text field. It stays hidden until you start dictating. When you press the Kass shortcut, Kass tells midna dictation is about to start, and midna shows the composer, fills it with whatever you'd already typed and focuses it before Kass looks. ↩ sends the draft to the agent as one paste. Esc hides it again, and an empty composer hides itself.

Plain shells: the line you're typing

Shell integration reports the line being edited and the cursor position (zsh line-editor hooks; prompt markers for bash and fish). Midna exposes that line as the text field's contents. When Kass inserts or replaces text, midna turns it into keystrokes the shell understands: cursor moves, deletes and a paste. Kass can read the field back to confirm the text landed.

Tested, and it works. We put a native text field into a real GPUI window and ran Kass's own steps against it from outside the app. Kass found a focused text field it can edit and read the words around the cursor ("git commit" | " -m "). It inserted " hello from kass" directly and confirmed the text landed exactly. Command Mode read back the selected word, and Enter sent the line on. Kass needs no changes, because midna isn't on its paste-only list. gpui-kit's built-in text field failed the same test: Kass found the window, not the field, and setting the selected text silently did nothing. So the composer has to be a native macOS field.

Design rules from the test

  • Midna moves keyboard focus between the composer and the terminal itself; GPUI doesn't take focus back on click.
  • Turn off smart quotes, dash substitution and autocorrect in the composer (' was turning into ’).
  • Never expose the terminal grid to macOS as an editable text field. When the grid has focus, Kass types the text in, which is the right behavior.
  • GPUI can't draw over a native field, so the command palette and popovers sit above the composer instead of covering it.

Still to check

  • ⌘ shortcuts while the composer has focus might fire twice.
  • Input methods (Japanese, Chinese) and real mouse clicks.
  • VoiceOver can't find the composer yet, because AccessKit replaces the window's list of accessible elements. Fix this by adding the composer to that list ourselves.
How it fits together

The daemon is the source of truth

Saggar's CLI drops request files in a folder the app checks about every 2 seconds, and the terminals live inside the app. In midna the shells live in midnad, a background daemon. They survive app restarts, agents can read them with no window open, and every event goes through a single stream.

One API, self-describing

JSON-RPC 2.0 over a Unix socket. rpc.discover returns the full OpenRPC schema, generated from the Rust types, so agents can look up what's available without docs. Every call includes the agent's identity and a reason, and every change is written to the audit log.

Why Ghostty's engine from the start

Alacritty's engine was only ranked first because Ghostty's needs a fragile build: one exact Zig version, and a linker fix on this Mac. That's a toolchain cost we pay once. We pin Zig and the Ghostty source in the repo, and CI builds with a known Xcode. Everything else favors Ghostty, and starting with it saves a migration later.

Webhooks

GitHub and Bitbucket events start the work

A pull request opens, CI fails, someone comments @midna: a trigger matches the event and either starts an agent session in the right project or runs a workflow. GitHub can't reach a laptop directly, so your server receives the webhook, checks its signature and passes it to midna over a connection midna opens itself. No port is ever opened on the Mac.

# .midna/triggers.toml  (per project, or global)
[[trigger]]
name    = "fix-red-ci"
source  = "github"                 # github | bitbucket
event   = "check_run.completed"
match   = { conclusion = "failure", branch = "main" }
run     = "agent"                  # agent | workflow
agent   = "claude"
isolate = "worktree"               # fresh branch per run
prompt  = """
CI failed on {{head_sha}}: {{output.title}}.
Find the cause and open a PR with the fix."""
approve = "none"                   # or "ask" before starting
limit   = 1                        # one run at a time
# .midna/workflows/review-pr.toml
name = "review-pr"
on   = { source = "bitbucket",
         event = "pullrequest:created" }

[[step]]  agent  = "codex"
          prompt = "Review PR {{pr.id}}…"
[[step]]  wait   = "agent.done"
[[step]]  run    = "pnpm test"
          on_fail = "notify"
[[step]]  post   = "pr.comment"   # report back
          body   = "{{steps.1.summary}}"

MVP events

  • GitHub: PR opened or updated, review requested, comment mentions, check or workflow failed, issue labeled, push
  • Bitbucket Cloud and Data Center: pullrequest:*, comment created, build status failed, push
  • Generic: any signed JSON POST, for your own tools

Guarantees

  • Signatures checked (GitHub X-Hub-Signature-256, Bitbucket X-Hub-Signature)
  • Each delivery runs once, even if GitHub or Bitbucket resends it
  • Missed events are queued while the Mac is asleep and delivered when it wakes
  • Every run is logged and listed in the sidebar, under the project it belongs to

Three ways for events to reach the Mac

Funnel tested on this Mac. We sent signed GitHub-style webhooks from the public internet to https://<mac>.<tailnet>.ts.net:8443. All 5 arrived with valid signatures in about 0.5 s each, and a forged one was rejected. Requests that come through Funnel carry a Tailscale-Funnel-Request header, so midna can treat them as anonymous. Midna's daemon can also read Tailscale's status without an admin password. One catch: the very first connection fails while Tailscale issues the certificate, so midna remote enable tailscale should make that first connection itself during setup.

Midna always keeps the webhook secret in the Keychain and checks every signature itself, so all three options run the same code. Switching options only changes the URL registered with GitHub or Bitbucket, and midna webhooks use funnel | relay <url> | hosted updates that URL for you, then sends a test event through the new route.

Updates

The app and the daemon update on their own

Kass already does this well: it downloads a signed update in the background and installs it on restart, with beta and stable channels. Midna uses the same release format through cargo-packager-updater, a standalone version of the Tauri updater Kass uses, so the release pipeline is one you already know. The difference: midna's shells live in the daemon, so restarting the app is harmless, and the daemon swaps versions with the shells still running.

Download

Every 6 hours the app checks for an update, then downloads and verifies it in the background (same channel setup as Kass).

Swap the app

The new app is installed when you quit, or straight away if no midna window is open. Terminals keep running in the daemon, so nothing is lost.

Check versions

The new app connects and compares versions. Each side also understands the previous protocol version, so the app and daemon can update in either order.

Test run

Only when the daemon's version has changed: the new daemon binary first loads a copy of the current state. If that fails, the old daemon keeps running and reports why.

Restart in place

The daemon saves each terminal's screen with Ghostty's engine and restarts itself as the new version, keeping the same process (the way systemctl daemon-reexec does). The shells stay attached and never notice. A watchdog falls back to the previous binary if the new one fails to start.

Reconnect + refresh

Clients reconnect and catch up on any events they missed. The new daemon updates its database, then refreshes the agent hooks, shell integration and the midna skill.

Tested, and it works. We swapped a test daemon in place twice while zsh, vim and claude --version ran under it. Results:
  • Programs kept the same process IDs and got no hang-up signal.
  • vim's screen came back byte-identical and still took typing.
  • Nothing was lost or duplicated, even across three swaps during a 2-million-line flood.
  • A swap took 23–365 ms, and clients reconnected within 24 ms.
  • A broken new version was caught before the swap, and the old daemon kept running.
  • launchd never saw a restart.

To fix:

  • Ghostty's screen export puts the cursor position in the wrong place and drops the window title and cursor shape. All have workarounds; report the bugs upstream.
  • An escape sequence cut off mid-swap is lost. Keep the unparsed bytes.
  • Launch the daemon through a symlink the update swaps, so a crash restarts the new version.

Agents can run midna update status | check | install | channel. Keeping the same signing certificate means macOS keeps the Accessibility and other permission grants across updates.

MVP scope

What ships first

Principle: if a person can do it, an agent can do it through the API. Every action is allowed by default. You add approval steps only where you want them.

Dictation + Kass input

  • Native composer field under agent terminals that Kass, macOS dictation and input methods all work with
  • The line you're typing in a shell exposed as a text field; edits typed into the shell and checked
  • Selected output readable (Read Aloud); terminal.input.get/set in the API
  • Works with Kass as it is today; tested end to end against Kass's own insert-and-confirm steps

Terminal core app

  • GPU-rendered terminal (libghostty-vt), tabs, splits, scrollback search
  • Projects: git repos found automatically plus midna init; terminals grouped under projects
  • Shell integration for zsh, bash and fish: prompt marks (to jump between commands) and current folder
  • Notification escape sequences OSC 9, 99 and 777, and the bell, feed the attention state
  • Terminal roles: shell, agent, monitor, one-shot
  • Config and theme in TOML that reloads live

Layout app

  • Command Deck: project sidebar, terminal area with splits, inbox
  • Overview grid sorted by needs-you; Focus mode with a queue strip
  • Rows show context: branch, ports, last message, cost
  • ⌘J jumps to the next terminal needing you; amber ring around panes waiting on you
  • Layout restored on restart

Daemon · midnad core

  • Owns the shells; terminals survive app restarts and crashes
  • Events for everything: tab opened, renamed or closed, process started or exited, status changed, output
  • Numbered event stream that can be replayed; clients that reconnect resume where they left off
  • Append-only audit log of who did what, why, and the rule that applied

CLI + API agents

  • midna covers projects, terminals, tabs, splits, windows, config, settings, keymap, policy, events and webhooks
  • JSON output everywhere; stable IDs plus queries (--match project:zonai,status:needs-you)
  • midna events --follow, and midna wait to block until a condition or prompt
  • midna schema / rpc.discover; midna mcp exposes all of it as MCP tools
  • Repeat-safe requests (a retried call doesn't run twice); each agent gets its own token tied to its terminal

Agent awareness agents

  • Hooks for Claude Code and Codex that parse JSON properly; set up with midna hooks install
  • Agents report their own status (working, needs you, done, failed) through an escape sequence or the API
  • Permission-prompt detection with an answer action; agents can launch sub-agents in new terminals and get a result back
  • Cost, context and rate-limit chip read from the agent's status line

Approvals you opt into policy

  • Rules in TOML: allow, ask or deny, by agent, action, project or command pattern
  • Approval cards in the inbox and in macOS notifications: approve once, approve for N minutes, or deny
  • Requests time out to deny; Touch ID can be required for high-risk rules
  • Agents can add rules. They can only remove one when a person told them to: midna checks that the current request was typed or dictated in midna's own window (not sent through the API). Otherwise removal becomes an approval card.

Windows app

  • Midna's own windows: bring to front, keep on top, snap to halves or thirds, move to another display, open and close
  • Pop any terminal or approval card out into a small window that stays on top (Satellites)
  • Other apps' windows: move, resize and raise (needs Accessibility permission; best-effort)

Triggers + workflows integration

  • GitHub and Bitbucket events start an agent session or run a workflow
  • Events arrive through your server over a connection midna opens; a tunnel is the option if you have no server
  • Signatures checked, no duplicate runs, events queued while the Mac sleeps, optional fresh worktree per run
  • Workflows: ordered steps (agent, wait, run, notify, comment on the PR)

Updates ops

  • Signed background updates with beta and stable channels
  • Daemon restarts as its new version in place, without closing terminals
  • Hooks, shell integration and the midna skill refreshed after each update

Accessibility everyone

  • VoiceOver: app controls through AccessKit, terminal text exposed as a native text area
  • Spoken announcements for status changes and approvals, throttled so they don't flood
  • Fully keyboard-driven; every action can be rebound; F6 moves between regions
  • Reduced motion, high-contrast themes, adjustable font and line spacing

  • Phone and other devicesEncrypted relay so you can approve from your phone and see live sessions
  • Tailscale gatewayReach the API from your own private network without exposing it publicly

gpui-terminal/		Stays at 120 fps through an 80 MB cat. Keystroke to screen in about 4 ms typical, 9 ms at worst (mostly waiting for the next screen refresh). A full-screen color repaint takes about 2.3 ms. vim, less, top, emoji, East Asian text and resize all display correctly.
  • The daemon owns the terminal; the app asks for a frame when it's ready and gets only the rows that changed. That makes it about 15× lighter on the app during heavy output, the same speed as running everything in one process, and makes reconnecting after an update trivial.
  • Draw characters cell by cell from a cache, not as lines of text.
  • Always build Ghostty's engine in its fast mode (ReleaseFast). One debug setting makes it about 5,000× slower.
  • Turn on Ghostty's grapheme mode, or multi-part emoji draw as several characters.
Agent status
agent-status/		Claude Code hook events reach the daemon in under 10 ms. Answering a permission prompt by typing 1 (Claude) or y (Codex) worked.
  • Hooks miss three moments: just after you approve a prompt, Esc while a tool runs, and Esc or ctrl-c on a prompt. Fill the gaps from the title spinner and the ✳ stop mark, plus a quick screen check.
  • The hook must send its data and exit 0 within about 5 ms. Slow hooks hold Claude up, and failing ones print errors in front of you.
  • Only type an answer after confirming the right dialog is on screen. A stray Enter updated Codex during the test. For Claude, answer from the permission hook instead.
  • Codex: use the screen and title until its hooks can be approved through midna's own Codex config folder.
Windows
windows/		Keep-on-top, snapping to halves, thirds and full, and pop-out windows that don't steal focus all worked, landing exactly where asked. Other apps' windows can be moved, resized, minimized and closed.
  • Build pop-outs as GPUI's PopUp windows. They're the only kind that shows over full-screen apps.
  • Bringing midna to the front from the background only works through the older activation call GPUI uses; keep an eye on it.
  • "Keep on top" for other apps can only re-raise them, which steals focus. Label it that way or leave it out.
  • Every window.* call returns the frame asked for and the frame actually set.
Install + updates
install-update/		The app is signed with your Developer ID and registers its daemon with macOS from Rust. An update installs in about 0.3 s and the daemon swaps versions without dropping sessions. The Accessibility permission carries over from v1 to v2, and the daemon is covered by the app's permission.
  • An app that's already running doesn't notice new permissions, so midna restarts itself after you grant one.

Decision log

What's settled

Composer

Appears only when dictation starts, then hides after sending or Esc.

Accessibility means Kass

The goal is Kass working fully in every terminal: read context, voice edits, direct insertion and Command Mode. The composer and the exposed shell line are MVP items, and the first thing we prototype.

Approval rules

Agents can add rules. They remove one only when a person directed it: midna checks that the request was typed or dictated in midna's own window, or a person approves a removal card.

UI framework

GPUI via gpui-kit. Its built-in text input isn't usable by Kass, so the composer is a native macOS text field embedded in the GPUI window.

Terminal engine

libghostty-vt from day one, with Zig and the Ghostty source pinned in the repo.

macOS support

As old as the stack allows. GPUI (via Zed) runs back to macOS 10.15, with 12+ recommended. The daemon registers with launchd's newer API on 13+ and falls back to a plain launch-agent file below that. Proposed minimum: macOS 12, Intel and Apple Silicon. CI will tell us whether 10.15 and 11 come nearly free. Ghostty's own app is moving to macOS 14, but we only use its core engine, which doesn't depend on AppKit.

Webhooks

Webhooks are GitHub and Bitbucket events that start sessions or workflows. Three ways to receive them: Tailscale Funnel (free), the midna-relay server you deploy yourself (free), or midna's hosted relay (paid only). Sending midna's own events out is later.

Saggar

No migration or import.

Prototypes

Both passed: Kass edits a native composer in a GPUI window, and the daemon restarts in place without the shells noticing. Code is in midna/spikes/.

Updates

Kass-style background updates plus restarting the daemon in place.

Still open

  1. Kass handshake. Tested 20/20 runs with about 3 ms of delay: the composer was focused before Kass looked every time. Kass's side (about 80 lines) is being built in its own worktree, on branch feat/dictation-handshake. Apps that haven't opted in get no added delay.
  2. Composer layout. GPUI was slow to make room for the composer when it appeared, so it briefly covered the last terminal rows. Either treat it as an overlay on purpose, or force a GPUI redraw when it appears.
