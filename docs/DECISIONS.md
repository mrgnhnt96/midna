
## Foundation (midna-proto / midnad / midna-cli)

- **midna-proto API for clients** (usable now):
  - `midna_proto::Client::connect(paths::socket_path())`, then `call::<T>(method, params)` / `call_value`.
  - `client.subscribe(Some(since_seq))` returns an iterator of `Event`. For `window.command` pushes, use `Subscription::next_notification()`, which returns `Notification::{Event, WindowCommand, Other}`.
  - `Client::attach_stream(socket, session, cols, rows, cell_w, cell_h)` returns `AttachStream` with `want()`, `resize()`, `input()`, `next_frame()`. Use `writer()` for a cross-thread write half.
  - `Frame`, `Cell`, `RowData` and the `F_*` flags live in `midna_proto::frame`. `Frame::decode` returns `Result`.
- **Wire forms of tagged enums:**
  - `RuleScope`: `{"kind":"global"}`, `{"kind":"project","id":"p_.."}`, `{"kind":"session","id":".."}`.
  - `ApprovalScope`: `{"kind":"once"}`, `{"kind":"minutes","minutes":N}`, `{"kind":"session"}`, `{"kind":"always"}`.
  - `Resolution`: `{"kind":"approve","scope":{...}}`, `{"kind":"deny"}`, `{"kind":"dismiss"}`, `{"kind":"done"}`, `{"kind":"restart"}`.
  - `TriggerAction`: tagged by `kind`.
  - `SettingType`: `{"kind":"enum","options":[..]}`.
- **Caller hint.** Clients may add `caller: {session?, role?}` to any params object.
  - `Client` fills `session` from `MIDNA_SESSION` automatically.
  - `role:"agent"` lets a connection downgrade itself; nothing can upgrade to human. Human status comes only from the peer executable check.
  - Any call carrying `caller.session` is treated as `agent`.
- **Settings catalog** is in `midna_proto::settings::SETTINGS`, so the GUI can render it without a round trip. Extra keys added beyond the contract:
  - `agents.claude.statusline`
  - `policy.default`
  - `policy.request_timeout_secs`
  - `git.refresh_secs`
- **Extra error code:** `5` = not implemented yet (trigger/webhook stubs, `daemon.upgrade`).
- **Timestamps** are second-precision RFC 3339 UTC, produced by `midna_proto::time`, a hand-rolled module so we don't need a date crate.
- **No async client yet.** The blocking client on a background thread is enough for GPUI.
- **midnad concurrency.** midnad uses plain threads, not tokio:
  - one reader thread and one writer thread per connection
  - one engine thread per session, which owns the `!Send` libghostty Terminal
  - a PTY reader thread and a reaper thread per session
  - a 200ms saver/expiry loop and a git refresh loop

  `Core` (state plus runtimes) sits behind one mutex. The lock order is core, then the event log. Nothing waits on an engine thread while holding core.
- ~~**The event log lives fully in memory** for replay and insights, and is loaded from `events.jsonl` at startup. That's fine for now; it needs compaction or windowing later.~~ done: monthly files + a 62-day in-memory window (see "Closing the open TODOs").
- **Sessions don't survive a daemon restart yet.** That's the re-exec phase. On startup, leftover sessions are marked `exited` with reason "daemon restarted".
- **Human-only calls from agents:**
  - They return error `2`.
  - `rule.remove` points to `rule.request_removal`.
  - Every other human-only call (for example `project.remove`, or `settings.set` on a `human_only` key) raises an `approval` needs-you item with a deferred call. If the human approves it, the daemon runs that call as the human. Agents can never approve deferred items.
- **Approval scopes become rules:**
  - The new rule is `allow` with an exact, glob-escaped matcher on the action's value, and `origin` is set.
  - `once` creates no rule.
  - `minutes(n)` creates a session-scoped rule (project, then global, if there's no session) that expires.
  - `session` creates a session-scoped rule.
  - `always` creates a project-scoped rule, or global if there's no project.
- **`policy.request` for unmatched `tool` actions has no opinion.** It returns `source:"default"`, and `midna hook claude` prints nothing, so Claude's own permission flow decides. A rule that matches with `ask` raises a midna approval and blocks.
  - On timeout it returns `ask`/`timeout`, withdraws the item, and `needs_you.resolved` carries `{"kind":"timeout"}`.
  - The Claude PreToolUse hook entry gets `timeout: 600`.
- **Policy defaults table** (`policy.default` = `auto`): `cli` values matching `close --force*`, `restart*`, `replace*`, `project remove*`, `rules remove*` or `settings reset*` ask; everything else is allowed.
- **Agent verbs are policy-checked as `cli`/`window` actions:**
  - `close <id>` and `close --force <id>`
  - `restart <id>`
  - `<action> <target>` for window commands
  - Agents can't close a working session without `force` (error `4`).
  - Closing another session's terminal while `agents.may_close_idle` is false turns a default allow into ask.
  - `window.command` from agents needs `agents.may_move_windows` for everything except `front` and `open_screen`.
- **Expired rules are deleted** and emit `rule.expired`.
- **Extra event kind:** `session.git` (`{git}`), emitted when a terminal's GitInfo changes.
- **Exit status:**
  - Exit 0 gives `exited`.
  - A non-zero exit or a signal gives `failed`, with `exit_code` set.
  - A failed `monitor` or `agent` session also raises a `failed` needs-you item (bulk-safe, with a screen excerpt). Resolving it with `restart` restarts the session in place under the same id.
- **Titles:**
  - `Session.title` always tracks OSC 0/2.
  - A `session.title` event is only emitted when the text *after* a leading spinner glyph changes, so the log isn't flooded.
  - The glyph heuristic, for agent sessions only:
    - `◐◑◒◓` or Braille spinners mean working.
    - `✳`/`✻` mean stopped. Stopped while working, with no prompt on screen, gives `idle` and ends the turn. Stopped while needs-you, with no prompt on screen, gives `idle` and clears the prompt item.
    - Working while needs-you gives `working` (the approval was answered).
- **Hooks map to status** through the spike's state machine. `SessionEnd` gives `idle` (the process exit sets `exited` or `failed`).
  - `Notification` permission_prompt raises a `permission_prompt` needs-you item, which is cleared automatically when the agent moves on.
  - Approving or denying that item sends Enter or Esc, but only if the screen check sees a prompt.
- **Cost.** Claude's status line is the only real cost signal, so midna registers `statusLine` (`midna hook claude statusline`, which prints `model · $cost`) in its own `claude-settings.json`. The setting `agents.claude.statusline` (default true) turns it off. `agent.cost` carries `delta_usd` and `total_usd`.
- **Insights definitions:**
  - turns = `agent.turn_started`
  - messages = `agent.prompt_submitted`
  - approvals = `needs_you.resolved` with `approve`
  - working and waiting time = time spent in `working` and `needs_you` according to `session.status` events
  - Ranges are local-day based. `vs_previous` is the period of the same length immediately before.
- **Launching processes:**
  - Absolute argv runs directly.
  - Bare names and single-string commands run through `$SHELL -l -c`, so the user's PATH applies. Agents launch as `$SHELL -l -c 'exec "$0" "$@"' claude --settings …`.
  - Terminals get `MIDNA_SESSION`, `MIDNA_PROJECT`, `MIDNA_SOCKET`, `MIDNA_HOME` and `TERM_PROGRAM=midna`, with the CLI dir prepended to `PATH`.
  - `CLAUDECODE` and similar variables are scrubbed.
- **The CLI is found via** `MIDNA_CLI_PATH`, else a `midna` next to the midnad executable (or one directory up), else `midna` on PATH.
- **GUI fan-out.** Human connections that call `events.subscribe` also receive `window.command` notifications. `window.list.gui_connected` probes them with a blank line, which clients ignore.
- **Frame streams:**
  - A new attach gets one credit and a full frame.
  - When several clients attach to the same session, each one accumulates merged dirty rows while it has no credit.
  - Frames are built only when at least one client has credit.
- **CLI exit codes:**
  - `0` ok
  - `1` for RPC errors `1`/`2`/`3`/`4`/`5` and internal errors
  - `2` for usage errors, `-32602` and `-32601`
  - `3` when the socket is unreachable
- **CLI free text.** Free text that contains flags goes after `--`, e.g. `midna check command -- git push --force`.
- **MCP.**
  - Tool names are method names with `.` replaced by `_`.
  - `stream.attach` and `events.subscribe` are left out, since streaming can't work as a one-shot tool.
  - Results come back as both text and `structuredContent`.

## GUI (midna-app)

- **Lenient client model.** `midna-app/src/model.rs` mirrors the proto domain types with `#[serde(default)]` and `#[serde(other)]` fallbacks, so a newer daemon with extra fields or enum values doesn't blank the UI. A test round-trips proto's strict `Session` and `Segment` through it. `Resolution` and `ApprovalScope` are re-exported from proto, so resolve calls use the daemon's exact wire form.
- **Backend seam.** The `backend::Backend` trait has `call`, `subscribe` and `attach`:
  - `DaemonBackend` uses `midna_proto::Client` for calls and `events.subscribe`. It reconnects every 1s and shows "midnad not running" while the daemon is down.
  - `stream.attach` uses a raw socket plus proto's frame codec. `StreamWriter` can't shut its socket down, so detaching would otherwise leak a blocked reader thread per terminal switch. Suggestion for proto: add `AttachStream::shutdown()`.
  - `FakeBackend` (`MIDNA_BACKEND=fake`) serves the Main.dc.html sample data. It runs a real in-process PTY and libghostty engine per session (cargo feature `fake-engine`, on by default).
- **GUI caller identity.** The GUI calls `set_caller(None)`, so an inherited `MIDNA_SESSION` never makes it look like an agent. Dev runs need `MIDNA_APP_PATH=<target>/debug/midna-app` on midnad to be treated as human.
- **Refresh model.** Events only mark what's stale (projects, sessions, needs, settings, insights, rules, webhooks, header and row scripts). A 40ms coalesced refetch reloads the lists. Header and row scripts also refresh every 15s, because git changes don't always raise events.
- **Needs-you outranks status.** A session with a pending needs-you item is drawn as "needs you" (dot, attention line) even when its own `status.state` is still idle. Example: a shell waiting in `policy.request`.
- **Initial selection** is the first session with an approval item, then the first needs-you session, then the first session. `MIDNA_SELECT` overrides it.
- **"At root" shortcuts** (`keys.new_*_root`) call `session.open` without `project_id`, and the daemon picks the root.
- **Root.** `session.open` with no `project_id`, no `cwd` and no caller project opens at root: `project_id` `"root"` (`ROOT_PROJECT_ID`, never a real project) with cwd `$HOME`. So ⌘T, ⌘K asks, and the root shortcuts all work with zero projects. `"root"` can also be passed explicitly, and an agent in a root terminal opens its siblings at root.
- **New agent** reuses the agent most recently started in that project, defaulting to Claude.
- **⌘W** (`CloseWindow`, fixed binding) in the main window closes the selected terminal (`session.close`) and selects its sidebar neighbour; a busy one (working / needs you) needs a second ⌘W within 2 s; with nothing selected it closes the window. In Settings or a pop-out it closes that window. A menu, overlay (⌘K, needs-you) or screen (Rules, Triggers, Insights) in front is closed first, like esc. All three screens have "Back to terminal  esc" in their header (`screen_kit::back_btn`). The status bar's "Set up webhooks" opens Triggers with the delivery-path picker open; "Add a trigger" opens Triggers at the list.
- **⌘Q is hold-to-quit** (`HoldToQuit`, `ui::quit_hold`): 2.5 s, with the window dimming and a ring filling around a ⌘Q badge (eased, glowing head). Releasing ⌘, a reported Q key-up, or the window losing focus cancels. macOS often drops Q's key-up while ⌘ is held, so releasing ⌘ is the reliable cancel. The hold also polls the live ⌘ state (`NSEvent.modifierFlags`) every tick, so a release that never reaches GPUI as an event still cancels, and a tap never quits. The menu's "Quit midna" quits at once, and so does ⌘Q in Settings or a pop-out (no overlay there). Terminals keep running in midnad.
- **Switching terminals** reuses the pane's measured size for the new attach (no second PTY resize) and keeps the old screen up until the new one has its first frame (max 250 ms). Keys go nowhere during the swap.
- **Rename**: double-click a terminal's name in the header or sidebar for an inline field; ↩ or blur saves (`session.rename`), esc cancels.
- **Pop-out** is a normal window raised to `NSFloatingWindowLevel` (above other apps, like PiP), with a "Keep on top" pill to drop it to normal level. It was `WindowKind::PopUp`, which sat above everything with no way to send it back.
- **Pop-out moves the terminal, it doesn't mirror it.** Popping out takes the terminal out of the main window (the main pane selects its sidebar neighbour, a split showing it closes) and it stays out while its window is open (`ui::popout::Popped`, an app global). Its sidebar row keeps its place with a small pop-out mark; clicking it (or any `select`) brings the window forward instead of showing it in the main pane. The pop-out's dock button (`Icon::DockIn`, next to "Keep on top") closes the window and selects the terminal in the main window; closing the window any other way also puts it back in the sidebar, unselected.
- **Sidebar**: the needs-you pill only shows when something needs you. Root terminals (no project) are listed first, without a heading; ⌘1–9 count projects only.
- **Closed projects.** A project with no terminals leaves the sidebar (`MainWindow::groups` drops it), but it isn't removed from the daemon, so its rules and commands stay. ⌘O, a typed path, or ⌘K "Go to project" (now `Run::OpenProject`, marked "closed, opens a terminal") reopens it with a new shell. ⌘1–9 follow the visible order. With nothing selected, ⌘T opens in the first visible project, else at root. The sidebar and empty pane show "Open project…" whenever no terminals are open.
- **Quit.** A finished ⌘Q hold calls `cx.quit()` directly. Dispatching the `Quit` action did nothing in the installed bundle, though it worked unbundled.
- **Status bar**: `midnad` (hover explains it's the background daemon; no terminal count) · Policy · webhooks · triggers. Webhooks shows "Set up webhooks" while off or until first clicked; triggers shows "Add a trigger" while there are none or until first clicked. Both open Triggers. Clicks are remembered app-side in `$MIDNA_HOME/app-state.json` (`{"seen": [...]}`), not in daemon settings, to keep Settings uncluttered.
- **Sidebar order**: click and drag a terminal row to move it within its group (root or project). No handle or drag preview; the row moves live as the cursor passes a neighbour's middle. The order is app-side (`app-state.json` `order`, terminal ids); terminals not in it keep daemon order after the dragged ones, and moving to the next/previous terminal follows the sidebar order.
- **Multi-select terminals**: ⌘-click a sidebar row (or rail dot) to add it to the selection or take it out; ⇧-click (or ⌘⇧-click) selects every visible row from the anchor (the last row clicked without ⇧) to the clicked one, across projects, skipping popped-out terminals and rows hidden in folded projects. The clicked row is the one shown, with the accent bar; the others get `accent_soft`. A plain click, esc, or showing a terminal outside the selection (⌘]/⌘[, needs-you) clears it. ⌘W closes every selected terminal (one confirming second ⌘W if any is working or needs you) and selects the nearest remaining row below, else above. Dragging a selected row moves its group's selected rows with it as one block. State lives in `MainWindow::marked` and isn't saved.
- **Open project.** `keys.open_project` (⌘O), the "Open project…" ⌘K row and an accent button (sidebar and empty pane, shown while there are no projects) open a folder picker, then `project.add`, then go to the project's first terminal or open a shell there. Typing a folder path into ⌘K (`~/…` or `/…`, must exist) offers "Open <path> as a project" as the first row. With no current project, ⌘K drops its duplicate "at root" rows and the ask scope is root only.
- **Several main windows** (`windows.rs`). `keys.new_window` (⌘⇧N, any window) and midna ▸ New Window open another main window, cascaded 28 px from the active one, with no terminals (open whatever you want in it).
  - Every terminal shows in exactly one main window, the one that owns it (a pop-out counts as part of the window it came from). Ownership is app-side. `app-state.json` → `windows` (most recently used first) keeps each window's bounds, terminals and selection; launch reopens them (a window on a display that's gone comes back centered). It's saved 400 ms after a move, resize, selection or ownership change. A window you close is dropped from it, but quitting keeps every window. `MainWindow.sessions` stays the full list (needs-you, ⌘K, rules use it); `groups()` (sidebar, ⌘1–9, next / previous, selection) keeps this window's.
  - A terminal nobody owns yet (opened by an agent, a trigger, a schedule, the CLI) goes to the home window: the main window focused last. A window that selects an unowned terminal (⌘T, ⌘K, a `session.open` result) takes it. Selecting one another window owns (⌘K, needs-you cards, `midna window front`) brings that window forward and selects it there.
  - The home window alone posts notifications and takes `updates.command`; a `window.command` with a target goes to the target's window. A notification click (app-level, not per window) and the "you're looking at it" check follow the terminal to its window or pop-out.
  - Dragging sidebar rows (one, or the ⌘-selected block) onto another main window moves them there (its sidebar shows "Move here" while you're over it); released outside every window they get a new window under the cursor. Same-window drags still reorder. GPUI has no cross-window drop, so the source sidebar converts the release point to screen coordinates and checks `cx.window_stack()` front to back.
  - Closing a main window that has terminals while another is open asks (`ui/close_window.rs`): move them to the window used last (↩), close them all (`session.close`, their pop-outs too), or cancel. "Don't ask again" saves the answer in `windows.close_with_terminals` (ask | close | move, Settings ▸ General). The last main window just closes; midna quits and the shells keep running. ⌘W in a window with nothing selected goes through the same question.
  - The needs-you count and cards are the same in every window; opening a card's terminal (or ⌘K "Go to") brings its window forward. ⌘K lists this window's terminals first, then the other windows'. When two windows have terminals with the same name, ⌘K and the needs-you cards say "this window" / "other window".
  - `app-state.json` is shared: saving merges the other windows' `seen` and keeps their terminals' places in `order`.
  - The composer's text view and Kass have one sink each; their events go to the active main window (else the home window).
- **Project folders (`projects.roots`).** A list setting (new `SettingKind::PathList`: a JSON array, or comma/newline-separated text on the CLI; entries must be absolute or start with `~/`; agents may set it). `project.discover` (`midna projects discover`, MCP `project_discover`, read-only) lists the direct subfolders of each root, most recently modified first, skipping hidden ones. A subfolder that isn't a git repo but holds repos is replaced by those repos (`~/Development/rust/midna`). The list is capped at 500 and flags the folders that already are projects. There is **no "Other projects" section in the sidebar**. The empty pane and ⌘K (before anything is typed) list up to 5 **recently opened** projects under "Recent": closed projects ordered by `last_opened_at`, which `session.open` stamps. Folders under the roots **never** appear in that list. ⌘K finds them only when searched for, as "Open project <name>", and picking one calls `project.add` and then opens a shell. The app fetches `project.discover` with every projects/settings refresh and whenever ⌘K opens. Root terminals still start in `$HOME`. **Adding a folder** never needs the CLI. "Add project folder…" (a link on the empty pane, and a ⌘K row) opens ⌘K in a path-search mode: the query starts with `commands::FOLDER_PREFIX` ("Project folder: ~/") and only folder rows show. The first row, "Add <dir> as a project folder", appends `<dir>` to `projects.roots` via `settings.set`. The rows after it are the folder's subfolders, or the ones that start with the typed name (case-insensitive). ↩ or ⇥ on a subfolder types it in, and there is no "Ask an agent" fallback in this mode. The empty pane has no title, the Recent list (max 5) and one hint line ("⌘T terminal at root · Add project folder…").
- **Script segments.** The GUI accepts three optional hints on a segment, all ignored if absent:
  - `icon`: `branch` | `pr` | `dot`
  - `mono`: bool
  - `join`: bool, which attaches the segment to the previous one with a single space
  
  The fake backend uses them to match the design (branch icon, mono diff stats, PR icon). Suggestion for the daemon's built-in `github` script: emit them so the real header matches the board exactly.
- **Approval banner** shows for `approval` and `permission_prompt` items, or any item carrying `approval`. "Approve for 1 hour" is `minutes: 60`.
- **Keybindings** are rebuilt from `keys.*` on every settings refresh; invalid strings are skipped with a log line. ⌘1–9 select projects, ⌘D is split (not built yet), and Escape closes overlays and screens.
- **Terminal input.** Non-text keys (arrows with xterm modifier params, ctrl-*, alt-as-meta, F-keys, shift-enter → `ESC CR`) are handled in `on_key_down`. Printable text goes through GPUI's input handler, which makes IME composition work: marked text is drawn at the cursor and the candidate window is anchored there. ⌘V paste honors bracketed paste. Mouse-drag selection plus ⌘C/⌘A work on the visible grid.
- **Theme mapping in the terminal.** Cells using the engine's default fg/bg take the theme's `--fg` / `--term`, so light mode reads correctly. Explicit ANSI colors are drawn as-is.
- **Screenshots while the screen is locked.** Occluded windows stop drawing on macOS. The dev-only cargo feature `snapshot` (enables `gpui-kit/test-support`) plus `MIDNA_SNAPSHOT=out.png` draws the main window offscreen with `window.draw` + `render_to_image` and quits. These captures have no native traffic lights. `screencapture -l` only works while the screen is unlocked.

## Triggers and webhooks (midnad `webhooks/`, `rpc/trigger.rs`, CLI `triggers.rs`)

- **Trigger lifecycle.** `needs_secret` (created, no secret) → `draft` (secret set, never enabled; "ready to enable") → `active` ⇄ `paused`. Only `active` triggers fire.
- **Human-only rules:**
  - Agents can create triggers (always `needs_secret`); an agent-created trigger raises one `secret_needed` needs-you item (one per trigger; the item carries the new `NeedsYou.trigger_id`).
  - `trigger.set_secret` stays `human_only` in the catalog, but an agent calling it does **not** go through the deferred-approval path, because the deferred call would persist the secret. Instead it raises (or reuses) the `secret_needed` item and the secret is dropped.
  - `trigger.set_enabled` is no longer `human_only` in the catalog: anyone may pause. Enabling by an agent uses the deferred approval (`defer_to_human`); if there's no secret yet it raises `secret_needed` instead. A human enabling without a secret gets error `4`.
  - An agent changing the `action` or `source` of an active or paused trigger sends it back to `draft` (a human re-enables). Name, event, filter, `github_hook_id` and `session_name_template` changes don't.
  - Agents may remove triggers that aren't enabled; removing an enabled one is deferred to the human.
  - Settings `webhooks.path` and `webhooks.relay_url` are now `human_only` (otherwise `settings.set` would bypass `webhooks.configure`). `webhooks.port` stays agent-writable (an existing test relies on it, and it's low risk).
- **Secrets.** Keychain generic password, service `com.mrgnhnt.midna.webhook`, account = trigger id (`security-framework` 3). `MIDNA_SECRETS=file` → `$MIDNA_HOME/secrets/<id>`, 0600, dir 0700. Cached in memory after the first read. Never returned over RPC (Trigger has `secret_set`, `secret_set_at`, `secret_store` only); audit summaries already redact `secret`. Removing a trigger deletes its secret.
- **Receiver.** `tiny_http` on `127.0.0.1:<webhooks.port>`, its own thread, one short thread per request. It runs only when `webhooks.path != off`, or when `MIDNA_WEBHOOKS_PORT` / `Config.webhooks.port_override` is set (tests use `0` = any free port; `webhooks.status.receiver.bound_port` reports it). A 1s manager loop rebinds when the path/port changes. Routes: `POST /hooks/github`, `POST /hooks/bitbucket`, `GET /hooks/health`.
- **Pipeline.** Inline (before answering): headers → dedupe → candidate triggers (same source, secret set) → HMAC-SHA256 check against each candidate's secret (constant time via `hmac::verify_slice`) → event/filter evaluation over the *verified* triggers only. Answers 202 (401 bad/missing signature, 400 missing headers or non-JSON, 200 duplicate, 200 ping). Then, after answering on the same thread: run actions, record the Delivery, emit `trigger.fired` (per trigger) and `trigger.delivery`.
  - Verdicts: `verified` (fired), `filtered` (a trigger listens to this event but a filter, the action, or its state said no; `trigger_id` points at it), `no_trigger` (nobody listens, or no trigger for that source has a secret yet), `bad_signature`, `replayed`, `recovered`.
  - A `pull_request.opened` trigger "listens" to other `pull_request` actions, so `synchronize` is `filtered` ("wants pull_request.opened, got pull_request.synchronize"), matching the design.
  - Event syntax: GitHub `event[.action]`, globs allowed (`pull_request`, `pull_request.*`); Bitbucket the event key (`pullrequest:created`, `pullrequest:*`). Filters (repo, branch, action, label) are case-insensitive globs.
  - Dedupe by delivery GUID against recorded deliveries (except `bad_signature` ones and replays) plus an in-flight set. Duplicates get 200 and are **not** recorded again.
  - Every non-duplicate request is recorded (cap 500 in state; oldest pruned). Payloads of authenticated deliveries are kept in `$MIDNA_HOME/deliveries/<d_id>.json` (0600) for replay.
  - A verified GitHub `ping` sets `github_hook_id` on the triggers whose secret signed it (and whose repo filter matches), so recovery needs no extra setup.
  - Delivery gained (additively) `action`, `repo`, `subject`, `http_status`, `eval` (one line per listening trigger), `triggers_fired`, `sessions_started`, `recovered`, `replay_of`. Trigger gained `last_fired_summary`, `enabled_at`, `secret_set_at`, `secret_store`, `github_hook_id`, `session_name_template`.
- **Actions.** Run with a `Ctx` whose actor is `{kind: trigger, name: <trigger name>}` (new `Ctx.as_actor`, agent-level privileges), through `rpc::session::open`.
  - `start_agent`: prompt = rendered template; terminal name = `session_name_template` or `<trigger name> #<pr>`.
  - `run_command`: a `monitor` terminal; **every substituted value is shell-single-quoted** so PR titles can't inject shell.
  - `attention`: a bulk-safe `note` needs-you with `trigger_id`.
  - Templates: `{{pr.number}} {{pr.title}} {{pr.url}} {{repo}} {{branch}} {{sender}} {{url}} {{event}} {{action}} {{subject}}`, any payload path (`{{pull_request.head.ref}}`), and `{{pr.X}}` → `pull_request.X` / `pullrequest.X`. Unknown keys render empty.
  - `MIDNA_AGENT_BIN` / `Config.agent_bin` replaces the agent executable (tests use `/bin/echo`).
- **Replay** skips the signature check (it was verified on arrival), runs against all current triggers through the same filters, and always records verdict `replayed` with `replay_of`. `bad_signature` deliveries can't be replayed (error `4`).
- **`trigger.test`** is a pure dry run of one trigger (verdict `verified` = would match), with the rendered prompt/command in `summary`; nothing is recorded.
- **Tailscale Funnel.** CLI = `MIDNA_TAILSCALE`, else `/Applications/Tailscale.app/Contents/MacOS/Tailscale`, else `tailscale` on PATH. `webhooks.status` reads `tailscale status --json` (DNS name, online, `funnel` node capability + funnel ports) and `tailscale funnel status --json` (is `<dns>:8443` proxied to our port with `AllowFunnel`), cached 15s. `public_url` = `https://<dns>:8443/hooks/github`. `webhooks.configure{path: tailscale_funnel}` runs `tailscale funnel --bg --https=8443 http://127.0.0.1:<port>` as a direct child (no shell) with a 20s timeout and returns `enable_url` if Tailscale prints a `https://login.tailscale.com/…` link. Leaving Funnel runs `tailscale funnel --https=8443 off` only if :8443 points at our receiver. `health` is `healthy|down|off` (the GUI treats `healthy` as ok).
- **Relays.** `self_relay` / `midna_relay` can be selected but report `health: down`, "relay not available yet"; no client yet.
- **Missed-delivery recovery** (`webhooks/reconcile.rs`, best effort): ~3s after startup, on wake (wall clock jumped > 60s past the monotonic clock), and via the new `webhooks.reconcile` method. For each active GitHub trigger with `github_hook_id` and an exact `owner/repo` filter: `gh auth status`, then `gh api repos/{repo}/hooks/{id}/deliveries?per_page=100`; for each GUID not seen, delivered within 3 days **and after the trigger's `enabled_at`** (so enabling doesn't replay history), fetch `…/deliveries/{id}` and process the request payload as `recovered` (no HMAC: the payload comes from GitHub over authenticated `gh`). `MIDNA_NO_GH` disables it. Filtered recovered deliveries keep `filtered` with `recovered: true`.
- **New event kind** `trigger.removed`. New method `webhooks.reconcile`.

## Real agents (Claude Code 2.1.288, Codex 0.160.0; see `docs/STATUS-agents.md`)

- **Hooks registered in `claude-settings.json`:** SessionStart, UserPromptSubmit, PreToolUse, PermissionRequest, PostToolUse, PostToolUseFailure, PermissionDenied, Notification, Stop, StopFailure, SubagentStop, SessionEnd. Tool events use matcher `*`. `PermissionRequest` is required: 2.1.288 sends it the moment its permission dialog opens. `Notification`/`permission_prompt` arrives only ~6s later, and only if nobody answered. The prompt item's title is `permission <Tool(arg)>`.
- **Keys the daemon injects follow the app's keyboard mode.**
  - The engine mirrors libghostty's kitty keyboard flags into `RtHandle.kitty`.
  - When the flags are non-zero, Enter is `CSI 13 u` and Esc is `CSI 27 u`. Otherwise they are `\r` and `\x1b`.
  - Claude enables the protocol as soon as the terminal answers the query. After that a bare `\r` only inserts a newline.
  - `session.input {enter:true}` writes the text, waits 150ms, then sends the encoded Enter. Text plus CR in one read is treated as a paste.
  - Prompt answers (`needs_you.resolve` on a `permission_prompt`) use the same encoder.
- **Messaging an agent is `session.input` (`midna send`); images ride along as pasted paths** (verified 2026-10-04 against Claude Code 2.1.289 and Codex 0.160.0):
  - One-line and multi-line text both arrive as one message, and a message sent mid-turn is accepted (Claude queues it as the next turn; Codex folds it into the running one, as it does for typed input).
  - `images` (CLI `--image PATH`, repeatable) are copied into `$MIDNA_HOME/images/` (ASCII name with no spaces; non-PNG/JPEG/GIF/WebP converted with `sips`; copies older than a week pruned). Each copy's path is then sent as its own bracketed paste, 250ms apart, before the text. Both agents turn a pasted image path into `[Image #N]` and read it.
  - Every image is checked before anything is typed, so a bad path refuses the call and leaves the terminal untouched.
  - The CLI makes paths absolute against its own cwd, since the daemon's differs.
- **Env scrub widened.** The scrub list now covers the parent Claude session's markers (`CLAUDE_CODE_CHILD_SESSION`, which turns transcript saving off, and the session id, messaging socket/token, exec path, `CLAUDE_PID`, `AI_AGENT`, `CLAUDE_EFFORT`). It also covers `CLAUDE_HANDOFF_*`, Codex's thread/sandbox markers, and Saggar's `SAGGAR*`, so the user's global hooks can't attribute a midna agent to a Saggar terminal. User configuration variables are kept.
- **Title heuristics are agent-aware** (`agent_title_hint`):
  - Claude: `◐◑` working, `✳` stopped. It shows `✳` while its permission dialog is up.
  - Codex: a Braille spinner while working, printed twice (`⠧ ⠧ | dir`). When the turn ends the spinner is simply dropped, so a non-empty Codex title without a spinner counts as stopped.
  - `title_text` strips every glyph word, so spinner frames don't emit `session.title`.
- **Stopped titles settle before they count.**
  - A stopped title while `working`/`needs_you` starts one watcher thread (`settle_pending`). It waits 1.5s, then re-checks every 1s while a prompt is on screen.
  - It acts only when the title is still stopped and the screen check finds no prompt: `working` becomes `idle` and the turn ends; `needs_you` becomes `idle` and the prompt item clears.
  - Why: Claude flips to `✳` before it draws the dialog and before `PermissionRequest`. Esc on the dialog fires no hook and doesn't change the title, so only the screen can show the prompt is gone.
- **Spinner while `needs_you` means "answered" only if no prompt is on screen and no midna `approval` is open for the session.** Claude keeps spinning while a PreToolUse hook blocks on midna.
- **Codex turns start from the title.** Codex has no prompt hook without trusting hooks, so a spinner while `idle`/`done` starts a turn and sets `working`. This applies to Codex only; Claude's title keeps spinning for seconds after `Stop`.
- **Codex `notify`:**
  - The notify that belongs to Codex's internal task-title generation (separate thread; reply `{"title":…}`, input "Generate a concise, single-line task title…") is ignored.
  - `agent.prompt_submitted` now carries the input text.
  - If the title ended the turn less than 15s earlier, the notify doesn't open a second turn.
- **midna approvals mark the agent `needs_you`** while `policy.request` blocks (reason `approval <value>`), and set `working` ("approval answered") afterwards. This applies to sessions launched as agents, and to terminals whose agent has sent hooks.
- **Screen check tightened** to the bottom 25 non-empty lines:
  - Claude matches `Do you want to …` together with a `1. Yes` option.
  - Codex matches `Would you like to run the following command` / `…make the following edits`, `Yes, proceed`, or `Allow command?`.
  - The bare `Approve` / `Do you want to` patterns are gone. Claude's folder-trust dialog and Codex's hooks-review dialog must never match, because Enter there means "No, exit" or "Review hooks".
- **Exit by SIGINT/SIGHUP (or code 130) is `exited`, not `failed`.** Codex 0.160.0 quits on a double ctrl-c by re-raising SIGINT.
- **`Stop` still maps to `done`** (finished, unseen), not `idle`. Every other route to "not working" (interrupts, dismissed prompts, `SessionEnd`) gives `idle`.
- **CLI:** `--help` on any verb prints usage and never runs the verb. `midna open --help` used to open a terminal.

## Daemon upgrade, restart and stop (midnad `upgrade.rs`, `install.rs`, `server.rs`, `term.rs`)

- **Same-PID execv, as in the spike.** `daemon.upgrade{binary_path}` (human only) runs `<new> --selftest` synchronously; failure = error `1`, nothing touched, `daemon.upgrade_failed` emitted. Success answers `{ok, binary, sessions}` and hands off ~150ms later on a thread (so the answer is flushed before the exec). Agents, `midna daemon upgrade <path>` and `midnad --upgrade-to <path>` all go through the existing human-only deferral, i.e. a needs-you approval; approving it runs the upgrade as the human.
- **Selftest contract.** `midnad --selftest` round-trips a terminal snapshot in-process and prints `{"ok":true,"version",…,"handoff_versions":[1]}`. The old daemon refuses unless our `HANDOFF_VERSION` is listed. The handoff format is versioned so a future binary can keep resuming old handoffs.
- **Handoff = `$MIDNA_HOME/handoff/`**: `handoff.json` (pid, from/to/fallback binary, home, socket, app_path, listener fd, event seq, watchdog secs, and per session: id, pid, alive, master fd, its `st_rdev`, title, cursor shape, cursors, scrollback rows, half-parsed tail, agent `in_turn`/`last_cost`) plus raw `<sid>.primary.vt` / `<sid>.alt.vt` (raw files, not hex-in-JSON). state.json is flushed just before. Removed after a successful resume; an unresumed one found by a plain start is moved to `handoff.stale-<ts>` (its PTYs died with the process).
- **Pausing output.** PTY readers now `poll` (50ms) instead of blocking in `read`, so a global pause takes effect; an in-flight counter (SeqCst store/load pair) proves no reader holds bytes the engine hasn't been sent. The engine `Snapshot` message is FIFO behind those bytes. Unread output stays in the kernel buffer for the new image (the flood test checks nothing is lost or duplicated).
- **Snapshots are non-destructive.** Exporting the primary screen needs `?1049l`; the engine then replays its own alt export in place, so the old image keeps running correctly if the exec fails.
- **libghostty export workarounds** (`engine.rs`): `CSI H` before the export; CUP re-issued last from our own cursor reading (after title/DECSCUSR); NULs stripped (OSC 7); title replayed as OSC 2 and cursor shape as DECSCUSR from RenderState; the half-received trailing escape / UTF-8 sequence is tracked on every feed (`incomplete_suffix`, capped at 64 KiB) and replayed last. **New bug found:** the export drops trailing blank rows, so with scrollback the restored content sat one+ rows low and the next line overwrote the last one (the spike missed it). Fix: write the rows, then scroll (`\r\n`, still under the full-screen region) until the scrollback count matches the original, then the trailing state (CUP/DECSTBM/tabs), located as the last `SGR 0` followed only by escapes. Not carried: DECSC saved cursor, origin-mode-relative CUP.
- **Exit tracking.** The reaper waits on the pid (`waitpid(pid)`), not a `std::process::Child`, so adopted sessions use the same code. Verified: after a same-PID execv the shells are still our children and exit codes still arrive. When waitpid says ECHILD (the watchdog fallback, below) it falls back to kqueue `EVFILT_PROC NOTE_EXIT`, with no exit code (macOS only gives statuses to the parent). The reaper also waits (≤500ms) for the PTY reader to drain before `on_exit`, so the failed-item screen excerpt has the last output.
- **Watchdog.** Before the exec the daemon starts `<old binary> --upgrade-watchdog <handoff.json>`, which inherits the PTY masters and listener (CLOEXEC cleared for exactly this window, with PTY spawns locked). It exits when `handoff/resumed` appears. If the new image dies (its parent pid changes) or hasn't resumed within `MIDNA_UPGRADE_WATCHDOG_SECS` (default 10; then it SIGKILLs it), the watchdog execs the old binary with `--resume … --fallback`: terminals survive, the daemon pid changes, exits come from kqueue. Not covered: a new image that resumes and crashes later (the watchdog is gone by then; that's an unclean death). The "launchd restarts the stable symlink and resumes from the handoff" variant isn't possible on its own: once the last process holding the master fds dies, the PTYs are gone, so a plain start only sets the handoff aside.
- **`daemon.restart`** (not human only: nothing is lost, and same-user `kill -TERM` could do it anyway) = the same handoff onto `MIDNA_HOME/bin/current/midnad` when we run from there, else our own executable (a rebuilt binary is picked up; the selftest guards it).
- **Signals.** SIGTERM = graceful restart (falls back to a stop if the handoff fails). SIGINT = stop. `MIDNA_SIGTERM=stop` restores "kill ends it" for scripts. Handled on a thread via a self-pipe (a handoff can't run in a signal handler). **Tradeoff:** a crash/SIGKILL/OOM still loses every PTY (sessions are marked `exited`, "daemon restarted", as before); SIGTERM keeps them but means `kill <pid>` no longer stops midnad. launchd sends SIGTERM on bootout, so the SMAppService phase must stop the job with `daemon.stop` first (or set `MIDNA_SIGTERM=stop` in the plist) — TODO for that phase.
- **Stop policy (the orphaned-monitor bug).** The old SIGTERM handler `_exit`ed without signalling anything, and `Handle::stop` sent SIGHUP/SIGKILL from a thread that died with the process. Now `daemon.stop` (human only), SIGINT and an in-process `Handle` drop all run `server::stop_daemon`: SIGHUP + SIGCONT to **every process group in each terminal's session** (found with `proc_listallpids` + `getsid`, plus the tty's foreground group), wait up to 1.5s, SIGKILL the groups still alive, then exit. Processes that left the session (setsid/daemonized) are left alone. An upgrade/restart never signals anything.
- **During a handoff** every mutating method except `daemon.*` gets error `4` ("upgrading; retry"), so nothing lands after the snapshot. In-flight `policy.request` waiters lose their connection (the hook prints nothing, Claude's own prompt decides); their needs-you item survives in state.
- **In-process daemons can't re-exec** (`Config.owns_process`, set only by the binary): `daemon.upgrade`/`restart` return error `4` in tests; the real path is covered by `tests/upgrade.rs`, which drives copies of the built binary.
- **Stable location.** `midnad --install-self` copies the binary (and a sibling `midna`) to `MIDNA_HOME/bin/<version>-<sha256[..8]>/` and swaps `bin/current` atomically (symlink + rename). Upgrades don't install anything themselves; installing then `daemon.restart` is the intended flow for the SMAppService phase.
- **CLI:** `midna daemon info|upgrade <path>|restart|stop`.
- **New events:** `daemon.upgraded {from:{version,binary,pid}, to:{…}, sessions_kept, sessions_lost, reason: upgrade|restart|sigterm, fallback}`, `daemon.upgrade_failed {to, reason, error}`, `daemon.stopping {sessions}`. New methods `daemon.restart`, `daemon.stop`; `UpgradeResult` in proto.
- **Finding (not changed):** libghostty's `max_scrollback` (10_000) behaves as a byte/page budget, not lines: about 800 rows survive at 100 columns. Probably worth raising for real use.
- **App TODOs (not edited; app agents own it).** The app already survives an upgrade: the events thread reconnects (≤~1.75s), replays from its last seq, and `Conn::Connected` after a drop re-attaches the selected terminal. ~~Gaps: (1) the status bar flashes "midnad not running" during every upgrade — show "midnad restarting…" when the drop follows a `daemon.upgrade`/`restart` call, or for the first ~3s of any drop; (2) a frame stream that ends on its own (sink `end()`) while the events connection survives stays `Ended` — re-attach when the session is still running; (3) pop-out/satellite terminal windows need the same re-attach on reconnect; (4) one in-flight control `call` fails with a transport error at the exec — retry once on `Io` errors.~~ done (all four), see "Closing the open TODOs".

## Kass composer and handshake (midna-app `composer.rs`, `kass.rs`)

- **Protocol source.** The `~/Development/ts/kass-dictation-handshake` worktree doesn't exist; the handshake landed on Kass `origin/main` as e69d4f53 (`docs/DICTATION_HANDSHAKE.md`, read only). midna follows it: `dictationWillBegin {pid, mode: dictate|command}`, reply `dictationReady {pid}` within 150 ms, `dictationDidEnd {pid, outcome: inserted|cancelled|failed}`. Opt-in is either Info.plist `KassDictationHandshake = true` (bool) or posting `handshakeSupported {pid}`. midna isn't bundled yet, so it posts `handshakeSupported` at launch and every 3 s. **TODO for the bundling phase:** add `KassDictationHandshake = true` to Midna.app's Info.plist.
- **Listener thread, and a finding.** Distributed notifications are *not* delivered to a background thread's own CFRunLoop. CFNotificationCenter and NSDistributedNotificationCenter's selector form both deliver on the **main** run loop whatever thread registered (verified with a Swift probe: a background thread running `CFRunLoopRun` got nothing until main ran its run loop). The block form with an `NSOperationQueue` is delivered off main. So `kass.rs` has its own thread (`midna-kass`) with its own CFRunLoop, which owns the re-advertise timer, and the observers run on a private serial `NSOperationQueue`. Unit test `delivers_off_main` proves delivery while no thread runs the main run loop. Showing the composer must still happen on main; events reach the window over a channel (WillBegin → Ready measured at 0.4–9 ms).
- **When midna answers.** Only notifications with our pid. WillBegin is ignored (no reply, so Kass carries on as before) unless the main window is the active window and the terminal pane is showing with nothing over it (no ⌘K / needs-you / Rules / Triggers / Insights). Any WillBegin/DidEnd, even for another pid, sets "handshake detected" for Settings.
- **Composer = native `NSTextView` in an `NSScrollView`**, a sibling above the GPUI view (as in the spike), positioned every paint onto a GPUI `canvas` inside the box drawn after Main.dc.html (`mode=dictating`): accent box (no "Kass · listening" pill), `❯`, field, "↩ send to <terminal> · esc cancel". It grows with its text up to 8 lines, then scrolls. Subclass `MidnaComposerTextView` reports first-responder changes, edits, ↩ and Esc.
- **Two focus layers.** GPUI's view receives `performKeyEquivalent:` for every key before the text view. If GPUI focus stayed on the terminal, its key handler would eat ↩/Esc. So while the text view is first responder, GPUI focus is on `Composer::focus` (context `MidnaComposer`), which binds ⌘V/⌘C/⌘X/⌘A/⌘Z/⇧⌘Z to the text view (the app has no Edit menu). Blurring that focus (⌘K, a click elsewhere, another screen) hands first responder back to the GPUI view.
- **The GPUI view must hold AppKit's first responder whenever the composer is hidden.** Otherwise plain keys and modifier changes (⌘'s release, which cancels the ⌘Q hold) go to a hidden field or the bare window and are dropped, while ⌘-shortcuts still work. A user lost typing after dictating (2026-10-04). So focus is handed back before the field is hidden, the hidden field refuses first responder, and every render hands a stranded first responder (the field, the window or nothing) back to the GPUI view. The ⌘Q hold logs who held it.
- **Send.** ↩ = `session.input{id, text, enter:true}` to the terminal that was selected when the composer opened. Multi-line text is one bracketed paste when the terminal enabled mode 2004 (otherwise newlines as CR, like a paste); trailing newlines are dropped. ⇧↩/⌥↩ insert a newline. **Esc cancels: clears and hides** (Kass keeps its own captures). An existing draft is kept when a new dictation starts.
- **DidEnd.** Empty → hide and refocus the terminal. Text → stay open for review. `kass.auto_send` (new bool setting, default false) sends right away, but only when the outcome is `inserted` (or missing); `cancelled`/`failed` always stay for review.
- **Manual open.** `keys.composer` (new keybinding setting, default `cmd-shift-d`) opens the composer over the selected terminal, or refocuses it. Settings additions are in `midna_proto::settings` (catalog), the fake backend, and Settings' Agents section (`kass.auto_send` row; the Kass row says "Handshake detected" once any Kass notification arrived; settings.json view `status.kass`).
- **Not done:** pre-filling the composer with the shell's current line (needs shell integration); `command` mode gets no special handling beyond keeping the existing selection.
- **Dev hooks.** `MIDNA_DEBUG=1` logs every Kass notification and the ready latency. `MIDNA_KASS_ANY_WINDOW=1` skips the active-window check (testing while the screen is locked). `MIDNA_DEBUG_COMPOSER=<text>` (`\n` for newlines) opens the composer 1.5 s after launch. In `--features snapshot` renders the field's text is drawn by GPUI, because offscreen renders can't see native views.

## Packaging, install and auto-update (`packaging/`, midna-app `install.rs` / `updater.rs` / `lifecycle.rs`, `midnad --launchd`)

- **LaunchAgent = bundle binary + trampoline (as the spike proved).** The plist in `Contents/Library/LaunchAgents/` uses `BundleProgram Contents/MacOS/midnad` with `--launchd`. In that mode midnad sends its output to `MIDNA_HOME/midnad.log` and execs `MIDNA_HOME/bin/current/midnad` (running `install_self` first if `bin/current` is missing). So launchd restarts and logins run the version the last install chose, never a bundle that's being replaced. `MIDNA_TRAMPOLINED` stops a loop and is removed before terminals inherit the environment.
- **launchd policy.** `KeepAlive {SuccessfulExit: false}`: a crash restarts it, but `daemon.stop` (exit 0) stays stopped until the app kickstarts it. `MIDNA_SIGTERM=stop` is in the plist env, which resolves the upgrade phase's TODO: launchd's SIGTERM (unregister, logout) stops midnad cleanly instead of re-exec'ing. `ProcessType Interactive`, `ThrottleInterval 5`.
- **One version for every binary.** `midna_proto::VERSION` = `MIDNA_BUILD_VERSION` (set by `build-app.sh --version`), else `CARGO_PKG_VERSION`. Every `env!("CARGO_PKG_VERSION")` in midnad, the CLI and the app now uses it, so a test build can be 0.1.1 without editing Cargo.toml.
- **`daemon.info.binary`** (additive). It's the resolved path of the running midnad, captured once at startup (`install::running_binary`). `current_exe` reports `bin/current/midnad`, which resolves to the *new* target as soon as an install re-points the symlink. The first e2e run hit exactly that: the app thought the old daemon was current. The app upgrades when the binary **or** the version differs.
- **First launch is idempotent and runs every launch** (in the lifecycle thread):
  1. byte-compare the bundled midnad with `bin/current`; if they differ, `midnad --install-self`, then prune to current plus two
  2. SMAppService register (macOS 13+), or a legacy `~/Library/LaunchAgents` plist plus `launchctl bootstrap` on 12
  3. the CLI symlink
  4. connect; `daemon.upgrade` to `bin/current/midnad` if needed; `launchctl kickstart` if the agent is enabled but silent after about 4s

  The label comes from whichever plist is in the bundle, so test builds can use another label with no code change.
- **CLI link.** `~/.local/bin/midna` → `MIDNA_HOME/bin/current/midna`, a stable path, so updates never touch the link. The link is made only if `~/.local/bin` is on the *login shell's* PATH (`$SHELL -l -i -c`, 5s timeout; the app's own launchd PATH is useless for this), and never over something that isn't our symlink. Otherwise Settings offers "Install to ~/.local/bin" plus the `export PATH` line to add yourself. midna never edits rc files. `MIDNA_CLI_LINK_DIR` overrides the directory (tests).
- **Dev mode** = `MIDNA_DEV=1`, or an executable that isn't in `*.app/Contents/MacOS`. Nothing is registered and updates are off. If the socket is dead, the sibling `midnad` is started (it detaches itself; `MIDNA_NO_SPAWN=1` opts out). `MIDNA_BACKEND=fake` skips the lifecycle thread entirely.
- **Our own update format instead of Kass/Tauri's minisign.** The brief asked for ed25519 with an embedded key. The feed is one JSON entry (`version, pub_date, notes, url, sha256, size, minimum_macos, arch, signature`). The signature covers `midna-update-v1\nversion=…\nsha256=…\nminimum_macos=…\narch=…\n`, so the version is bound to the bytes (no "sign 0.1.1, label it 9.9" replay) and `url`/`notes` can change freely (mirrors). The crypto is `ring`, already in the lock via rustls, so no new crypto crate. The HTTP client is `ureq` 2 (rustls), blocking, on the lifecycle thread.
- **Defense in depth on the staged bundle:** sha256 check before extracting, then the same bundle id, the version equal to the feed's, `codesign --verify --deep --strict`, and the **same Team ID** as the running app when that one is Developer ID signed. Updates are newer-only by semver; there are no downgrades.
- **`updates.feed_url` is human-only.** The signature makes the URL harmless for integrity, but it decides where midna phones home, so agents can't change it. `MIDNA_UPDATE_FEED_URL` overrides it for tests.
- **Atomic swap = `renamex_np(RENAME_SWAP)`.** The staged app is moved next to the installed one (a `ditto` copy across volumes), swapped in one syscall, and the old one is deleted. On non-APFS volumes it falls back to two renames with rollback. The update downloads and stages under `MIDNA_HOME/updates/<v>/`, not next to the app, so `/Applications` holds no hidden staging directory while an update waits.
- **When it applies.** The status bar item or Settings' "Restart to apply" swaps, starts a detached `sh` that waits for our pid and then runs `open Midna.app`, and quits. If the UI hasn't quit after 5s, the lifecycle thread `exit(0)`s (the swap is already done). Quitting with an update ready applies it without relaunching (`on_app_quit`). The *new* app upgrades the daemon on its normal launch path, so there's no "post-update" special case: an app that's newer than its daemon always upgrades it.
- **No Accessibility relaunch.** Fix on Accessibility only opens the pane; the grant takes effect without relaunching midna, so there is no Relaunch button.
- **Headless subcommands of the bundle binary:** `midna-app --uninstall` (`daemon.stop`, SMAppService unregister, remove our CLI link; data is kept) and `--login-item-status`. The e2e cleanup uses them, and they're the documented uninstall.
- **Signing.** Inside-out with `--options runtime --timestamp` and an intentionally empty entitlements file. midnad is signed with identifier `<bundle id>.daemon` and the CLI with `<bundle id>.cli`. The first "Developer ID Application" identity in the keychain is used, else ad-hoc. Notarization is a separate opt-in script that is never run automatically (it uploads to Apple).
- **Test flavor instead of touching the real install.** `build-app.sh --bundle-id/--label/--env` produces `com.mrgnhnt.midna.test` with label `com.mrgnhnt.midna.test.daemon` and `MIDNA_HOME` in both `LSEnvironment` (app) and the plist's `EnvironmentVariables` (daemon). SMAppService accepted the test label with no approval prompt (status went straight to `Enabled`), and no TCC prompt appeared. `tccutil` was never needed.
- **Icon** is "Twilight tiles" (picked 2026-10-05 from canvas https://claude.ai/artifact/2GaEYxQgWhQKJQUVbaouCx, Tiles 3): Midna's own window as tiles on a dark squircle, a sidebar with teal/orange/lavender status dots, a lavender crescent in the main pane, a teal split pane with a block cursor and an orange status bar. `packaging/make-icon.py` draws it (stdlib-only PNG writer, then `sips`/`iconutil`) into `Midna.icns` and `Midna.png`; the site's `icon.png` files are copies of that PNG, and `site/public/favicon.svg` is the same design as SVG. After changing the design, rerun the script and copy the PNG to `site/public/icon.png` and `site/src/assets/icon.png`.
- **DMG window** is "Moon phases" (same canvas): a dotted arc from Midna to Applications with the moon waxing along it, a glow behind Applications and one line, "Drag Midna into Applications". Source `packaging/assets/dmg/background.html` (Inter, from `site/node_modules`), rendered by `scripts/render-dmg-background.sh`.
- **Fonts** stay compiled into midna-app (`include_bytes!`); the TTFs and OFL texts are also copied to `Contents/Resources/Fonts` so the licenses ship with the binary.
- **Not done:**
  - universal (x86_64) builds
  - the macOS 12 legacy LaunchAgent path is written but untested (no macOS 12 machine)
  - the RequiresApproval flow isn't exercised, because registration was Enabled immediately
  - ~~`midna update status|check|install` for agents (design notes) needs an RPC that reaches the app; not built~~ done (`updates.*`, `midna updates`)

## Terminal pane as a daily driver (keys, scrollback, selection, links, split, find)

- **The daemon encodes input; the GUI sends structured events.** libghostty-vt 0.2.2 exposes key, mouse, focus and paste encoders, viewport scrolling, terminal-owned selections (with a click/drag *gesture* state machine) and grid refs with OSC 8 URIs, so all encoding happens in midnad against the live terminal modes (`engine_input.rs`, a child module of `engine.rs`). No Rust re-implementation of xterm/kitty encoding was needed.
- **New stream tags** (client → daemon, `midna_proto::frame::ClientMsg`): `0x04` key (action, mods, GPUI key name, text), `0x05` scroll (wheel / lines / pages / top / bottom + pointer cell), `0x06` mouse (press/release/motion, button, mods, position in *cell units*), `0x07` focus, `0x08` paste. `0x03` stays raw bytes. Positions in cell units × the resize message's `cell_w/cell_h` give libghostty its pixels, so GUI scale never matters.
- **Frame trailer.** Frames end with an optional extension (`0xE1` marker): mouse tracking, alt screen, kitty flags, scrollbar (total/offset/len) and per-row selection ranges. Old decoders ignore trailing bytes and old frames decode with defaults, so no stream version negotiation. Selection changes alone produce a frame (`meta_dirty`), with no rows.
- **Routing in the GUI.** Every keystroke is a key event (with its `text`) except: ⌘ shortcuts, IME composition, and option-characters/dead keys when `terminal.option_as_meta` is off (those go through the IME input handler as raw text). Sending text keys as events too avoids a race: a kitty "report all keys" app gets CSI u even before the GUI has seen the frame that enabled it. Releases are sent only when the app asked for kitty event reporting.
- **Shift-Enter in legacy mode stays `ESC CR`** (midna's existing agent newline); under kitty it is `CSI 13;2u` from the encoder.
- **Wheel policy (daemon):** mouse reporting on and no shift → SGR/X10 wheel reports (≤20 per event); alternate screen without reporting → arrow keys (less, man); otherwise the viewport scrolls. Shift forces selection/scrollback over mouse reporting. Typing, pasting and raw input snap back to the bottom and clear the selection.
- **Selection is the engine's**, set through libghostty's gesture (1 click cell, 2 word, 3 line; alt-drag rectangle; drag past an edge autoscrolls — the GUI repeats the last motion every 60ms while outside). It is tracked by libghostty, so it stays on its text as output scrolls. Copy is `session.selection` (unwrap + trim, wide chars correct). **Tradeoff:** selection and viewport are per terminal, not per client — a pop-out and the main window attached to the same session share them.
- **Links:** ⌘-click → `session.link_at`: OSC 8 URI first, else a detected `http(s)://…` (trailing punctuation and unbalanced parens trimmed) or an existing path `path[:line[:col]]` resolved against the shell's OSC 7 directory, then the session cwd. Files open in `$VISUAL`/`$EDITOR` (read once from the user's login shell) as a new terminal in the same project (`+line`, or `-g path:line` for code/cursor/zed/subl), else `open`. No hover underline yet (would need a query per move).
- **Find (⌘F)** is `session.find`: plain-text scan of scrollback+screen (case-insensitive unless the query has capitals), scrolls the match to mid-viewport and selects it; ↩ older, ⇧↩ newer, esc closes.
- **New RPCs** (catalog + MCP): `session.key{id,key:"ctrl-c"}`, `session.scroll{to|lines|pages}`, `session.selection`, `session.select_all`, `session.link_at{col,row}`, `session.find{query,backwards}`. New setting `terminal.option_as_meta` (default true).
- **Split panes** (`ui/split.rs`): `MainWindow.split` holds a second `TerminalView` (own stream). ⌘D / the header button opens a new shell in the current project beside the selected terminal, or closes the split. The pane strip toggles side-by-side ⇄ stacked, moves the session to the main pane, or closes the pane (the session keeps running). Header/banner/composer keep following the sidebar selection. Selecting the split's session in the sidebar folds the split.
- **Fake backend** keeps its own engine: legacy key encoding, paste and viewport scroll only (no mouse reporting/selection/kitty).
- **macOS text editing in the input line** (`midna-app/src/term_edit.rs`; verified 2026-10-04 in zsh, Claude Code 2.1.289 and Codex 0.160.0):
  - ⌘← ⌘→ ⌥← ⌥→ ⌥⌫ ⌥⌦ ⌘⌦ send readline bytes (ctrl-a, ctrl-e, esc-b, esc-f, esc-DEL, esc-d, ctrl-k), as Ghostty and Terminal.app do, in every app. ⌘⌫ sends ctrl-u to agents. A ⌘⌫ binding (`keys.deny`) still wins while the selected terminal has an approval waiting, because GPUI tries bindings before key listeners and Deny passes the key on otherwise.
  - In a plain shell, ⌘⌫ sends ctrl-a, then erases what the cursor passed over once the frame shows it at the line start. zsh's ctrl-u clears the whole line, not just the part left of the cursor.
  - ⇧ plus any of those moves selects. The app moves its own cursor (so word and line edges are the app's and the prompt can't be selected), and midna draws the range from where the cursor started to where it is. Typing, ⌫, ⌦ or pasting replaces it: arrows to the right edge, ⌫ × the character count, then the text. The same applies to a mouse selection on the cursor's row (double-click a word, then type).
  - ⇧↑ ⇧↓ select by line. Inside an agent's multi-line input they send ↑ ↓. On its first row (the `❯`/`›` row) ⇧↑ selects to the line start instead, and on its last row ⇧↓ to the line end, as in a text field: Claude Code recalls history on ↑ from the first line. A shell's ↑ ↓ are history, so there they always select to the line start or end.
  - A selection across rows is erased by a job (`term_edit::EraseJob`), because its line breaks and the indents of continuation rows aren't visible as characters. It sends a count that can't be too many (the visible characters), then one key at a time, at most one per line break plus one. It stops when the screen shows the text before the selection, then the text after it, meeting at the cursor (on whichever row that ends up, since the input box moves as it shrinks). Checks wait for 120ms without frames, and input typed meanwhile is held and sent afterwards. A selection reaching the input's start (with ⌫) or end (with ⌦) skips the check and sends extra keys, which do nothing there. An emptied agent input shows a placeholder that a check couldn't tell from text.
  - Claude Code and Codex draw full-screen (alt screen + mouse tracking), so "skip full-screen apps" can't be the gate. Selection editing is on for non-alt-screen terminals and for agents: agent terminals (`session.agent`, read once per view with `session.get`), and Claude Code or Codex started from a shell. For the second, each time the alternate screen turns on the view calls `session.processes` and looks for a `claude`/`codex` command under the shell. The RPC returns a bare list; the CLI's `--json` wraps it. vim/less get ⇧← untouched.
  - ⌘↑ ⌘↓ in an agent go to the start / end of all the text, ⇧⌘↑ ⇧⌘↓ select to there. Neither agent has a key for that (ctrl-home/end do nothing), and ↑ on the first row recalls history in Claude, so midna counts the input rows to the prompt row (or to the last input row) and sends exactly that many ↑ ↓, then ctrl-a / ctrl-e. Both agents move a screen row per ↑ ↓, wrapped lines included. In a shell, ⌘↑ ⌘↓ still scroll the scrollback, and ⇧⌘↑ ⇧⌘↓ select to the line's start / end.
  - ⌘A in an agent's input box selects just its text, like a text field: the keyboard selection is anchored past the prompt glyph and the cursor is sent to the end with the ⌘↓ moves, so typing or ⌫ replaces it all. Outside the box (or in a shell) ⌘A still selects the whole screen.
  - ⌘C and ⌘X copy a keyboard selection from the screen (`term_edit::selected_text`, joining an agent's rows the way `input_text` does): the engine never sees it, so `session.selection` would come back empty. ⌘X then erases the selection as ⌫ does; a mouse selection is erased only once `session.selection` has returned, since the erasing keys drop the engine's selection. A selection outside the input (output, a full-screen app) is only copied.
  - Line start / end keys differ per agent. Codex's ctrl-a / ctrl-e at a line's start / end go on to the line above / below, but its Home / End stay put. Claude Code's Home / End move on, but its ctrl-a / ctrl-e stay put. So midna sends Home / End to Codex and ctrl-a / ctrl-e to everything else (`term_edit::for_agent`; the agent comes from `session.get` or the process probe). Skipping the key when the cursor "is already there" was tried and dropped: the cursor the view has can be a frame behind fast keys.
  - **Raw stream input now goes through the engine thread** like keys (`midnad/src/stream.rs`). Written straight to the PTY, it overtook keys still being encoded: ↓↓ then ctrl-e reached the app as ctrl-e ↓↓.
  - In agent terminals the left button makes midna's selection (sent as ⇧, the usual override), so a word can be double-clicked and typed over. A plain click with no drag is passed to the agent afterwards, so click-to-place-cursor still works. Wheel and other buttons still go to the agent.
  - **The engine now sends a frame when only the cursor moves.** Claude answers esc-b with a bare cursor move and no dirty rows, so the client's cursor (drawn and used for selection) used to stay where it was.
- **Dev driver** `MIDNA_DEBUG_TERM="run:ls;wheel:-200;drag:0,5,10,5;key:cmd-c;shot:x;quit"` dispatches real GPUI events (it draws first, so it works with a locked screen); in that mode links and copies are logged instead of opening apps or touching the pasteboard. `MIDNA_FPS=1` logs frames/renders per second.

## Closing the open TODOs (rules feed, palette, updates, reset, permissions, reconnect, event log, terminal, text input)

All items from the TODO sections above and the "Remaining gaps" list. New methods are in the catalog (so in `rpc.discover`, `midna schema` and MCP), with CLI verbs. Tests: `crates/midnad/tests/ui_updates_reset.rs` (10), `eventlog` unit tests (4), `rpc::ui` unit tests (2), app tests for `link_span` and the field's word moves.

**Policy and rules (daemon).**
- **`policy.decided`** (new event kind) is emitted whenever the defaults table decides a `policy.request` or an agent CLI/window gate: `{decision, source:"default", default:<policy.default>, passthrough, action}`. `passthrough: true` marks an unmatched `tool` call (midna has no opinion; the agent's own prompt decides). `policy.check` stays side-effect free. Rule decisions are still `rule.fired`, so the two never double count. It's one event per agent tool call; that's the price of "Only real signals" in the feed.
- **Rules feed** reads `rule.fired` + `policy.decided` (history from `events.list{kinds:[rule., needs_you., policy.decided]}`): default rows say "no rule · default" (or "no rule · agent's own prompt decides", outcome "unsupervised"), have no rule to highlight, and a defaults-table `ask` is tied to its approval by the action value + session.
- **Dismiss/Done on a `rule_removal`** item clears `removal_request` like Keep (deny) does; the agent can ask again.
- **`rule.restore{rule}`** (human only; agents get the usual deferred approval): the removed rule object (from `rule.removed` or `rule.list`) comes back with its original id, author, origin and fired count; `removal_request` is cleared. Refused (4) if the id exists or it has expired; the scope's project/session must still exist. Emits `rule.restored`. The Rules Undo sends the rule it removed. CLI `midna rules restore <id>` finds the rule in the log.

**Settings.** `ui.ask.agent` (claude|codex, default claude) and `ui.ask.scope` (project|root, default project), agent-writable, section general. The palette's toggles and ⇥/⇧⇥ write them (optimistic, then `settings.set`); with an older daemon that lacks them the old "last agent in this project" default is used. They also show in Settings → Agents.

**`ui.commands`.** `ui.commands.list` → `{path, commands, invalid}`, `ui.commands.add{command, replace?}`, `ui.commands.remove{id}`; CLI `midna commands list|add|remove`. Backed by `$MIDNA_HOME/commands.json` (still the app's format, so scripts can edit it).
- Validation: non-empty title ≤80 chars; `run` required (`rpc|focus|project|screen|pop_out|prefill`; `resolve` is not accepted from the file, so a command can't approve things); `rpc.method` must be in the catalog and not a streaming method; params must be an object; screen and icon from fixed lists; id defaults to `user:<slug>`; duplicate id = error 4 unless `replace`; max 200. `added_by`/`added_at` are stamped.
- **Human-only methods are forced through the destructive two-step confirm** (`human_only: true`, `danger` set), because a palette row runs as the human: an agent could otherwise plant "Show status" that calls `daemon.stop`.
- Anyone may remove a command (it isn't a safety control, unlike rules).
- A file that isn't a JSON array is never overwritten (error 4). Hand edits are noticed by an mtime poll (1s) in the daemon's background loop.
- `ui.commands_changed` is emitted on every change; the app reloads its registry from `ui.commands.list` on that event, on connect and when the bar opens (falling back to reading the file for the fake backend / old daemons).

**`window.command{action: split}`** (`value: side|stacked|close`, `target` = session; close needs no target). **Decision: split is allowed by default** like `front` and `open_screen`: it only adds a view beside what the human is looking at (front replaces the view outright). It is still policy-checked as a `window` action `split <id>`, so a human can deny it with a rule. The app shows the session in the split pane (or toasts if it's already the main pane); `close` folds it. `open_screen` is now idempotent in the app (it used to toggle the screen off when already showing).

**Updates over RPC: the GUI owns the updater, the daemon proxies.** The updater (feed, signature, staging, the bundle swap and relaunch) lives in midna-app's lifecycle thread and needs the app's bundle and process, so moving it into midnad would duplicate it. Instead:
- `updates.report{status}` (human only, special-cased so an agent gets a plain refusal, not a deferred approval): the app reports its state on every change and on every (re)connect. The daemon keeps it in memory and emits `updates.status` when it changes.
- `updates.status` returns that report (`state: unknown|disabled|idle|checking|up_to_date|downloading|ready|installing|error`, versions, notes, channel, last check, `gui_connected`).
- `updates.check` (agents may: harmless) and `updates.install` (human only → needs-you approval; approving runs it) are forwarded to every GUI connection as an `updates.command{action, by}` notification, the `window.command` pattern; `updates.requested` is logged with `delivered`. The client's `Notification::Other` now reaches the app as `BackendEvent::Notification`. "install" with nothing ready, or in a dev build, toasts why.
- CLI `midna updates [status]|check|install`. Settings' update rows show those commands.

**`daemon.reset{keep_rules?}`** (human only): closes every terminal (SIGHUP, like close --force), resolves remaining needs-you items (blocked `policy.request` waiters get deny), clears deferred calls, removes triggers + their secrets, deliveries (+ stored payloads) and projects, resets every setting (via `settings.reset`, so `settings.changed` fires), optionally removes rules. Event log and `commands.json` are kept. Emits the usual per-item events plus one `daemon.reset {keep_rules, result}`. Settings → Danger zone has "Reset midna" (two-click confirm) next to "Reset settings". CLI `midna daemon reset [--drop-rules]`. Not undone: a Tailscale Funnel that `webhooks.configure` set up stays (resetting `webhooks.path` doesn't run `tailscale funnel off`).

**Permissions.** `permissions.status` reports what midnad can actually see: `AXIsProcessTrusted()` for midnad itself (the grant that matters is Midna.app's, which only the app can check, and it says so), notifications `not_requested` (midna posts none), login item from launchd's `XPC_SERVICE_NAME` or the legacy LaunchAgent plist. **App reconnect.**
- "midnad restarting…" (status bar and the disconnected card, need color) for the first 3s of any drop, and up to 30s when the log showed an accepted `daemon.restart`/`daemon.upgrade` audit just before; then "not running".

## Final hardening pass (security + robustness; see `docs/SECURITY.md`)

- **GUI identity** (`peer.rs`): signed builds require the peer to satisfy `identifier "<midnad's id minus .daemon>" and anchor apple generic and certificate leaf[subject.OU] = "<midnad's team>"`, checked by audit token. Unsigned builds keep the name rule; `MIDNA_APP_PATH` only in debug builds (and never from a release handoff file). Any peer inside one of our terminals is an agent.
- **`caller.session` is verified** against process ancestry / POSIX session (`rpc::bind_caller`): inside terminal X the claim must be X (else error 1); daemon-spawned helpers outside terminals (scripts, in-process tests) are trusted; otherwise the claim is dropped.
- **Dev drivers** in midna-app go through `dev.rs`, compiled in only with `debug_assertions` or feature `dev-drivers` (`build-app.sh --dev-drivers`, used by `packaging/e2e`).
- **Deferred approvals** show the exact call and its target and store a fingerprint (trigger definition, binary sha256); a changed target makes approval fail with error 4.
- **Agents can't answer permission prompts** by typing (`session.input`/`session.key` → error 2 while a prompt is pending/visible); agent `stream.attach` connections are view-only.
- **Custom header/row script paths** are human-only (agents may pick built-ins).
- **Policy precedence change:** within one scope, an `allow` the human created by approving "always" now beats `ask` (deny > approved allow > ask > allow). Before, "approve always" on a same-scope ask rule never took effect and the human was asked every time.
- **Webhooks:** dedupe by GUID *and* verified body sha256 (claimed only after the signature check); ≤30 unauthenticated rejects recorded per minute; ≤16 requests in flight; Content-Length precheck.
- **Trigger prompts:** payload values are wrapped in ⟦ ⟧ with a trailing untrusted-data note (`payload::render_prompt`); trigger-started agents run supervised (`triggers.agent_mode`, human-only, default `supervised`: Claude `--permission-mode default`, Codex `approval_policy="on-request"`, `sandbox_mode="workspace-write"`).
- **Connections:** 32 MB line cap, parse errors keep the connection, panics caught, 64 MB per-connection outbound cap (cut off, not buffered), 30 s write timeout, 512 connections max; terminal grids clamped to 1000×500.
- **Files:** `MIDNA_HOME` 0700, socket bound under umask 077 then 0600.
- **Palette:** `commands.json` entries can't resolve needs-you items, can't fake needs-you rows, and sensitive methods always need ↩↩ with the exact call as the confirm text (daemon and app both enforce).

## Image annotations (midna-app `annotate.rs`, `ui/annotate.rs`)

Design: the "D · Sheet + image strip" and "Added, not sent yet" boards (canvas https://claude.ai/artifact/9Qmeaeq6tEEV4debitzHB8). Screens: `docs/screens/annotate-*.png`.

- **Opening.** `keys.add_image` (new keybinding setting, default `cmd-i`), the header's image button, ⌘V in a terminal when the clipboard holds an image and no text (a screenshot), or image files dropped on a terminal pane or sidebar row open the sheet for that terminal with them added. ⌘I / ⌘V / ⌘E act on the focused pane (the split's when it has focus), otherwise the sidebar selection. A drop with no image files does nothing.
- **Dragging over.** Image files dragged over a pane focus it and give it an accent edge. Held over a sidebar row for 450 ms they select that terminal (spring-loaded). Drag moves reach every element, so a pane only reacts when its own hitbox is hovered, and the sheet's scrim occludes, so dragging onto an open sheet doesn't move focus behind it. Rows another main window shows are left alone; a popped-out terminal's row forwards the drop to its pop-out.
- **Every window has a sheet.** The sheet is a view (`AnnotateView`) that the main window and each pop-out host, like the queue panel; drafts are in the `Drafts` global and attachments in `Outbox`, so they follow a terminal between windows. The tray shows under the main pane, the split pane and a pop-out's terminal. Below 960 px wide (a pop-out) the sheet tightens: 12 px margin, a 220 px notes rail, no key hints on the tools, no file name in the toolbar. A pop-out shows the sheet's messages as its own toast.
- **One draft per terminal**, in memory: images, each with notes that are a pin (click) or an area (drag), stored as fractions of the image. Close / esc keeps the draft; ⌘I brings it back. No tool switch: a click pins, a drag boxes. Keys: ⌘− ⌘+ ⌘0 zoom (scroll pans), ⌘↑ ⌘↓ switch image, ↑↓ select a note, ↩ edit it (↩ again saves; `keys.note_newline`, default ⇧↩, starts a new line, and the field wraps), ⌫ remove it, ⌘V paste an image, `keys.approve` (⌘↩) Add to chat.
- **Attach, don't type.** "Add to chat" puts the draft in the `Outbox` app global and shows a tray under the terminal (Edit ⌘E reopens the sheet, Remove drops it). Nothing reaches the PTY until the next plain ↩ in that terminal (any `TerminalView` of it: main pane, split or pop-out). That ↩ becomes: each image path as its own paste, then a newline (Ctrl+J, so the notes start on their own line in Claude Code's prompt), then the notes as one paste, then ↩, 250 ms apart. Editing text already typed into a TUI's input isn't something midna can do reliably, so it holds the attachment instead.

## Agent work tracking and restart-into-the-same-conversation (midnad `agent_work.rs`, `restart.rs`, `procs.rs`)

Why: an agent update ("Update installed · Restart to update") or a midna settings change needs a fresh agent process, and restarting by hand means quitting Claude, finding the session id and resuming, without knowing what the restart would kill. Verified live against Claude Code 2.1.289; fixture `crates/midnad/tests/fixtures/claude-2.1.289-background.jsonl`.

- **What Claude reports.** Every main-thread hook carries `session_id` (= the conversation; hooks inside a subagent also carry `agent_id`) and `permission_mode`; the status line carries `version` and `model.id`. `Stop` and `SubagentStop` carry a full snapshot, `background_tasks` (`{id, type: shell|subagent|…, status, description, command | agent_type | server/tool | name}`) and `session_crons` (`{id, schedule, recurring, prompt}`), always present, empty when nothing is in flight; a finished task just drops out. `SubagentStart` / `SubagentStop` bracket subagents. PostToolUse reports a backgrounded shell as `tool_response.backgroundTaskId` and a background agent as `{isAsync, agentId}`. A finished task wakes Claude with a `UserPromptSubmit` whose prompt is a `<task-notification>` block, then a new `Stop`. Codex reports only its `thread-id` (notify).
- **Quirks handled.** Claude's internal prompt-suggestion agent fires a `SubagentStop` with an empty `agent_type` (no start) after most turns: ignored. A stopping subagent lists itself as still running in its own snapshot: dropped. A woken background agent fires `SubagentStart` again with the same id: deduped. A main-thread `Stop` clears the live subagent list (background agents are in the snapshot), so a `SubagentStop` lost to a crash can't block a restart forever.
- **State.** `Session.agent_info: AgentInfo` (persisted in state.json, so it survives daemon upgrades) holds the conversation id, transcript path, running version, model, permission mode, `update_available`, `background`, `subagents`, `crons` and a `restart: QueuedRestart {reason, queued_at, by, waiting_for}`. `session.agent` events fire when something material changes (not on status-line churn); the app refreshes sessions on any `session.*` event.
- **Processes.** `session.processes` (CLI `midna procs`) walks the OS process table under the terminal (libproc + `KERN_PROCARGS2`) and tags each process with the background shell task whose command it runs (Claude runs it as `zsh -c '…eval "<command>"'`). Subagents are not processes; they run inside Claude.
- **Process facts (verified).** Claude's background shells are `setsid`'d (own session and process group, no tty), so a terminal's process-group SIGHUP doesn't reach them; Claude itself kills them when it exits on SIGHUP/SIGTERM (`SessionEnd` reason `other`). After SIGKILL they live on, re-parented to launchd. A restart therefore SIGHUPs Claude, waits for it to be reaped, then SIGHUPs any process tagged with a background task that ended up orphaned (`stop_orphans`). Untagged leftovers (a daemon the agent started on purpose) are left alone.
- **Resume.** `claude --resume <id>` keeps the same `session_id` (`SessionStart.source = resume`), restores the conversation and its session crons (even `durable: false`), but not background shells or agents. So crons are shown but never block a restart; background work does. The resume command is rebuilt from the current midna launch command (current hooks/MCP/hint settings apply; supervised trigger agents keep `--permission-mode default`), without the initial prompt, plus `--model <current>` and `--permission-mode <current>` (unless `default`), then `--resume <id>`. Codex: `codex resume <flags> <thread-id>`. The old process is stopped and reaped before the new one starts, so two processes never write one conversation. Same session id, same tab; status `restarted (resumed)`, event `session.restarted {resume, conversation_id, reason, from_version}`.
- **`session.restart`** takes `{id, resume?, when: now|idle, force, reason}` (old `{id}` calls still work). `resume` defaults to true when the conversation is known. `now` is refused while background work or subagents are in flight unless `force`. `idle` queues; `session.restart_cancel` drops it; the process exiting drops it too (an exit is not a cue to restart). The needs-you `restart` resolution queues for update notes and restarts at once for failed terminals.
- **When a queued restart runs** (`restart::tick`, every 2s): not working / waiting on the human / mid-turn, no open approval or prompt, nothing in flight, the terminal quiet for `agents.restart_idle_secs` (default 60; output or a status change resets it), and Claude's input box on screen and empty (text between the last two `────` rules after `❯`). A dialog or menu covering the input box holds it. `waiting_for` lists what it's waiting for, in plain words.
- **Updates** (`restart::check_updates`, ~10s after start then every minute): for each live Claude terminal, either the status line's running version is older than `claude --version` (resolved through the login shell like a launch; `MIDNA_AGENT_BIN` in tests), or Claude shows its own `✔ Update installed · Restart to update` notice (`agent_work::claude_update_notice`: only the 3 rows above the input box's top rule count, so a quoted copy in the transcript doesn't match). The notice is the only signal when the terminal's status line is the user's own rather than midna's (no version is reported then). Either one sets `update_available`, then per `agents.restart_on_update`:
  - `ask` (default since 2026-10-05): **no needs-you item and no status change** (the user's call). When the terminal is open, a prompt sits where the approval banner goes (`ui/update_banner.rs`, `AgentInfo::update_prompt`): **Restart** (same conversation now; hidden while background work or subagents run), **When idle** (queues it), **Not now** (`session.update_decline` → `update_declined`; hidden until a newer update). A **Don't ask again** box makes the answer the global setting: `when_idle` with Restart / When idle, `off` with Not now.
  - `when_idle` queues the restart without asking; `off` only records it.
  - Codex has no running-version signal, so only manual/queued restarts apply to it.
  - A `claude` typed into a shell terminal gets the same prompt once midna adopts it (see "`claude` / `codex` typed into a shell terminal").
- **GUI.** ⌘K per terminal: "Restart X" (same conversation; hidden while work is in flight), "Restart X when idle" (sub-line says what it would wait for), "Restart X in a new conversation", "Cancel queued restart of X" (shows `waiting_for`). The sidebar row is unchanged (rows stay dot + name + icon + one attention line).

## Prompt fast travel (midna-proto `prompts.rs`, midnad `prompts.rs`, midna-app `terminal/prompt_nav.rs`; canvas https://claude.ai/artifact/3w3P59q3Gjor6cco9BkqFP)

- **The prompts** come from `agent.prompt_submitted` events, which now carry `conversation` (Claude's `session_id`, Codex's `thread-id`). Gives up after 12 s, after reversing direction 3 times, or when a page press doesn't move the view (a dialog such as `/cost` is open). It runs on its own thread; the GUI passes `wait: false`. A newer jump in the same terminal cancels the running one. A terminal that keeps its own scrollback (an agent not drawing full-screen) uses the engine's find instead, which scrolls to the row and selects it. `MIDNA_DEBUG_JUMP=1` logs each step.

Hovering the bar slides out a round → after the pill, like a notification's, that jumps to the prompt the pill names.
  - The rail has one tick per prompt, spaced by order (the agent's scroll extents are unknown, so ticks can't sit at positions). The bright tick is where the view is, and prompts from before a /clear are greyed. Hovering a tick shows its text; clicking jumps.

## Notifications (midna-proto `notify.rs`, midnad `notify.rs` / `rpc/notify.rs`, midna-app `notify.rs`)

- **The daemon decides, the app shows.** A `notify` thread reads the event log (`EventLog::listen`, so it never runs under `core`), maps signals to a category, checks `notify.enabled`, the terminal's override (`Session.notify`) and the global `notify.<category>` setting, dedupes (same category + terminal within 3 s, so a permission prompt and its approval are one), and logs `notify.posted` (`notify::Posted`). Muted or off notifications aren't logged; `notify.list` explains what applies.
- **Categories** (`midna_proto::notify::CATEGORIES`). On by default (`notify.<kind>`: recorded as `notify.posted`): `approval` (approval / permission prompt / question), `attention` (agent note or blocked), `failed` (failed process, turn ended in error), `turn_done` (turn of at least `notify.turn_done_min_secs` = 30 s, body = first line of the reply from Stop's `last_assistant_message` / Codex `last-assistant-message`, now carried on `agent.turn_ended` as `message`), `agent` (`notify.send`), `from_trigger` (a trigger's `notify` action). Off: `requests` (trigger waiting, secret needed, rule removal), `background` (an agent background task finished), `pr_checks` (pending → passing/failing, deduped per PR), `exited` (clean exit), `triggers`, `restarted` (non-human restart). Interrupts, dismissed prompts and exits never count as "finished".
- **Sounds**: each category has `notify.sound.<category>` (`none`, a /System/Library/Sounds name, or an imported file's name; defaults Glass for approval and attention, Basso for failed, Ping for agent, none for the rest) and `notify.volume.<category>` (0–100, range-checked through `SettingSpec::range`), scaled by the master `notify.volume` (0 = silent). It replaces the old `notify.sound` important|all|off. `UNNotificationSound` has no volume, so midnad renders the sound at its volume (`notify_media::rendered`: `afconvert` to 16-bit WAV, samples scaled, cut to 30 s since longer sounds make macOS play its default, cached in `MIDNA_HOME/notify/cache` by file and volume, unused for 30 days pruned), copies it into `~/Library/Sounds` as `Midna <sound>.wav` (`Midna <sound> <volume>.wav` below 100; rewritten when it changes, unused ones pruned after 30 days) and sends that file name as `Posted::notification_sound`. The app names it with `UNNotificationSound::soundNamed`, so macOS plays it with the banner, at the alert volume, under Focus and midna's sound setting. We first sent the cache file's absolute path, because `spikes/notify-sound` (macOS 26) played a file in $TMPDIR that way; in the real app on macOS 26.6 every banner played the default sound instead, on two Macs, so the sound now lives where `soundNamed` documents it looks. The cost: these files show in System Settings' alert sounds, hence the readable names. Tests (no real daemon) use `MIDNA_HOME/notify/banner` instead. We first had the app play the file itself with NSSound and post silently: the sound could play with no banner under Focus and wasn't tied to the banner's timing. NSSound is now only the fallback when rendering failed and the dev-build (osascript) path; Settings' preview uses it too, scaled by the alert volume (`com.apple.sound.beep.volume`) to match. midnad's own app-closed fallback still plays the file with `afplay -v`, which ignores Focus. `notify.send` plays the agent sound only with `sound: true`. `Posted` keeps `sound: bool` and adds `sound_file`/`volume`, so an older app still plays the default sound.
- **Images**: `notify.image` (every notification) and `notify.image.<category>` (empty = `notify.image`, `none` = no image). The app attaches the image as a `UNNotificationAttachment`. It attaches a temp copy, because the system moves the file it's given. osascript (dev builds, app closed) can't show images.
- **Imported files** (midnad `notify_media.rs`): `notify.import{path, use_for?}` copies a sound (aiff/aif/wav/mp3/m4a/caf) or image (png/jpg/jpeg/gif) of up to 10 MB into `MIDNA_HOME/notify/{sounds,images}`. The magic bytes are checked against the extension. A file is named by its file name: the same bytes imported again reuse it, and different bytes get `-2`, `-3`. `notify.media` lists the macOS and imported files with the settings that use each. `notify.remove{name}` deletes an imported file and resets the settings that used it. `settings.set` refuses a sound or image name that doesn't exist, and names can't contain `/` or start with `.`. Each import or removal emits `notify.media`. `notify.test{category}` posts that category's notification even while it's off, never deduped, with `test: true` so the app shows it even for the selected terminal.
- **Settings UI** (`settings_notify.rs`): "Notification sounds" has the master volume, then per category a sound picker (your sounds first, then macOS; Import sound…, and a trash icon on imported sounds), a − / + volume stepper in steps of 10, and ▶ preview. Choosing a sound or changing a volume previews it. "Notification images" has a thumbnail, a picker (Same as every notification / None / imported / Import image…) and a Test button per category. CLI: `midna notify media | import <file> --for <kind>|all | remove <name> | test [kind]`. `midna notify` shows each kind's sound, volume and image.
- **Banners** (2026-10-06; replaces `notify.when_focused`). Being on (recorded) and being pushed are separate: `notify.push.<kind>` = a macOS banner for a terminal you aren't looking at (default on only for `approval` and `attention`, the user: "turn off push notifications unless it needs you from background tabs"), `notify.push_focused.<kind>` = a banner for the terminal in front of you (default off for every kind). midnad puts both on `Posted` (`push` defaults to true when missing, so an old daemon still pushes everything) and the app decides (`notify::show`): banner, sound only (looking at it, would push elsewhere, no `push_focused`), or nothing. With no app running midnad shows only pushed kinds. Not per terminal yet.
- **Other settings**: `notify.when_app_closed` (default on: with no GUI connected midnad posts via `osascript`, shown as Script Editor; never in-process or with `MIDNA_NOTIFY_SYSTEM=0`, which smoke.sh and the upgrade test set).
- **Per terminal**: `notify.set{session, key, value}`; `enabled: false` mutes, `null` drops an override; emits `session.notify`. Header … menu has Mute/Unmute; a muted terminal shows a bell-off icon by its name. Agents may change any terminal's notifications (not human-only); the skill tells them to do it when asked.
- **App**: `UNUserNotificationCenter` from Midna.app (thread id = terminal id, so they group per terminal; a click selects it; a delegate shows banners while midna is frontmost). Authorization is requested on the first notification. A dev build (not a bundle) uses osascript. Replayed `notify.posted` older than 30 s are ignored. Settings ▸ Notifications lists every switch; Settings ▸ Permissions shows the real authorization state.
- **Not verified yet**: the native path in a signed Midna.app: the permission prompt, click-to-select, image attachments, and Midna.app itself playing a rendered sound (the spike proved the mechanism, not midna's wiring). Ideas not built: Approve/Deny buttons on approval notifications, a dock badge with the needs-you count.

## Shortcuts everywhere (2026-10-05)

- **Every action has a shortcut, and every shortcut is a `keys.*` setting** (catalog in `midna_proto::settings`; the fake backend derives its rows from it). `actions::SHORTCUTS` maps each setting to its binding; tests check that the two lists match and that no two defaults collide. ⌘D, ⌘E, ⌘W and ⌘Q used to be hard-coded and are settings now. New: needs-you cards ⇧⌘J, approve options ⇧⌘↩, next/previous terminal (unbound by default: ⌃⇥ would be taken from terminal apps), project … menu ⌥⌘P, fold project ⌥⌘F, rename ⇧⌘E, restart ⌥⌘R, terminal … menu ⌥⌘M, copy session id ⌥⌘C, mute ⇧⌘M, clear ⇧⌘K, split orientation ⌥⌘D, split to main ⌥⌘↩, other pane ⌘], pop out ⇧⌘O (in a pop-out it docks back), keep on top ⌥⌘O.
- **Built-in keys** (⌘1–9, ⌘C/V/A, find, list navigation, image-sheet tools, and similar) aren't settings. They're listed in `actions::FIXED` so the Shortcuts tab and key search can find them.
- **Tooltips show the keys.** `header::tip_keys(text, setting)` reads the bound keys when the tooltip opens (`actions::BoundKeys`, rebuilt in `bind_keys`), so a rebind shows up right away. Menu items carry a `key_chip`.
- **Settings ▸ Shortcuts** is a third tab (⌘3) that replaces the read-only Keybindings group in Rows. It has a search field (⌘F) and a key detector (keyboard icon, ⌥⌘K, like VS Code's "Record Keys"). While the detector is on, a `cx.intercept_keystrokes` hook scoped to the Settings window captures each keystroke before any binding runs, so ⌘W and ⌘Q are searched instead of run. It lists the shortcuts on those keys, matching any modifier order and the first stroke of a chord.
- **Rebinding by pressing keys.** Click a shortcut's keys (or "Set keys" when it's unbound), press the new keystroke, then ↩ saves or ⎋ cancels. The same keystroke interceptor catches the keys, so even ⌘W can be bound; plain ↩ and ⎋ can't, because they save and cancel. If another `keys.*` shortcut already uses those keys, the row says so and saving unbinds it, so two shortcuts never fight over the same keys. A built-in key on the same keys is only a warning. The row also has × (remove keys) and Reset (back to the catalog default). Right-clicking a row opens a menu with the same actions: Change keys…, Remove keys, Reset to default, Copy command. Single keystrokes only: chords can still be set through the CLI or by asking an agent. Dev: `MIDNA_SETTINGS_EDIT=<keys.* setting>` starts a rebind.
- Dev: `MIDNA_SETTINGS_VIEW=shortcuts`, `MIDNA_SETTINGS_KEYS=<keys>` (a preset key search), `MIDNA_SETTINGS_DEBUG_KEYS=a,b` (keystrokes through GPUI dispatch).

## Queued messages (midna-proto `QueuedMessage`/`SendWhen`, midnad `queue.rs` + `rpc/queue.rs`, midna-cli `queue.rs`, midna-app `ui/queue.rs` + `terminal/queue_pill.rs`; board `docs/design/Queue-E.dc.html`)

The user asked for queued messages as a feature of their own (local triggers' `send_to_session` could already wait for the agent). Canvas https://claude.ai/artifact/QWeZfgmJnhhRHEpmYTpG5e had A (stack under the terminal: too tall), B (header popover: too easy to miss), C (a separate queue screen: rejected, it must stay with the terminal), then D/E/F. The user picked E, a floating pill, moved to the bottom right, with a glow when a message is sent.

- **State.** `Session.queue: Vec<QueuedMessage>` and `Session.queue_paused`, saved in state.json, so a queue survives restarts and upgrades and goes away with its terminal. A message has `{id q_…, text, enter, images, when, by, queued_at, state waiting|sending|failed, error, trigger_id, waiting_for}`.
- **When.** `idle` (default), `idle_for {minutes}` (since the last output, prompt or status change), `at {RFC 3339}`, `after {session}` (that terminal is idle, or ended, or closed, *and* its own queue is empty). Each one also waits until the agent is ready.
- **Order is strict.** Only the first message is considered. A later message never jumps ahead of one that is waiting for a time.
- **Ready** (`queue::readiness`, moved out of `local.rs`) means all of these:
  - the terminal is not working and not waiting on the human (a custom-status label doesn't count);
  - no turn is open;
  - the title doesn't say working;
  - no permission prompt is on screen;
  - Claude's input box doesn't hold a draft. No input box found means "can't tell", so a shell goes ahead.
  It must hold for 1.5 s. After a submitted message, the agent has 5 s to look busy before "ready" counts again. A message typed without Enter lets the next one skip the draft check.
- **The sender.** One `queue` thread ticks every 500 ms and keeps `waiting_for` up to date for the first message. A message is typed on its own thread, as whoever queued it: a human message is typed as the human; agents and triggers go through `session.input`'s agent path, including its prompt-answer refusal. Multi-line text is pasted, then Enter is pressed. Sent messages leave the queue. A failure marks the message `failed` with a bulk-safe needs-you note and holds the queue until it is retried (`queue.update retry`), sent now, or removed. A message being typed can't be edited, moved or removed.
- **RPCs.** `queue.list|add|update|remove|clear|move|send_now|pause` (`session` defaults to the caller's own terminal; at most 50 messages). `send_now` ignores `when` and whether the agent is busy. Event `session.queue {action, id, text, left, paused}`. `queue_list` is read-only in the MCP allowlist.
- **Triggers.** `send_to_session` adds its steps to the queue (summary "Queued N steps for X") instead of running its own thread. A firing whose earlier steps are still queued is refused. Idle triggers skip a terminal while its queue has anything in it.
- **CLI.** `midna queue [list] | add <text…|-> [--idle 10m | --at 18:00|RFC3339 | --after <id>] [--no-enter] [--image P]… [--first | --position N] | edit | rm | mv <id> <to> | send-now | clear | pause | resume`. Positions count from 1 in the CLI.
- **App.**
  - **The pill.** Each `TerminalView` (main pane, split, pop-out) draws its own pill from the `QueueStore` global, which is synced from `session.list`. The pill sits right-aligned, 22 px from the right edge (clear of the prompt rail), just above the input box's top rule (the second-to-last `────` rule on screen). It follows the box as the box grows. With no box on screen it sits in the pane's bottom-right corner, above the "↓ N lines below" chip when that shows.
  - **Pill states.** "N queued · next when Claude is idle | after 5 min idle | at 18:00 | after api"; "· paused"; red "Couldn't send"; "Nothing queued" while the panel is open on an empty queue.
  - **The flash.** Only sending glows (the user's call: the pill already shows that something is waiting). On `session.queue sent`, the pill shows a green "✓ Sent · N left" with a 1.6 s glow (a GPUI `with_animation` on its box shadows) and holds that for 2.6 s. Adding, editing, moving, pausing and failing never glow. A failure turns the pill a steady red "Couldn't send" until the message is retried or removed, plus a toast in the main window. With macOS Reduce Motion on, the glow is a steady ring instead (`defaults read com.apple.universalaccess reduceMotion`, read once).
  - **The panel** (`Menu::Queue`) opens upward from the pill. The main window draws it at the pill's window-space anchor, so typing in its field never reaches the terminal under it. It has a list, a field, a "when" chip (⇥ cycles when idle / 5 / 15 / 30 min idle; times and other terminals are CLI/agent only), Queue / Save, and Pause / Resume.
  - **Keys.** ↑↓ select, ↩ queue (or edit the selected message when the field is empty), ⇧↩ send now, ⌥↑↓ reorder, ⌥⌫ remove, esc cancels an edit, then closes. Rows have hover buttons for send now, edit and remove.
  - **Opening it.** `keys.queue` = ⌘U (⌘J was taken by next needs-you), a click on the pill, or ⌘K "Queue a message for X".
  - **Every window has its own panel.** The panel is its own view (`QueueView`). The main window hosts one, and so does each pop-out (`PopOut.queue`, opened by its pill or ⌘U). The panel carries its own click-away layer. It tells its host when it closed, so the host can refocus its terminal, and when a call failed (the main window shows a toast; a pop-out logs it). The list gets only the height that is left above the pill (64–300 px), so in a short pop-out window the panel still sits above its pill and the list scrolls.
- **Dropped.** ⌥↩-in-the-terminal-to-queue: Claude Code uses ⌥↩ for a newline, and midna can't reliably read and clear what's typed in the agent's box. The image tray doesn't offer "Queue" yet (`queue.add` takes `images`).
- **Dev.** `MIDNA_DEBUG_SCREEN=queue|queue-sent|popout-queue` (`MIDNA_SNAPSHOT_WINDOW=last` snapshots the pop-out) and `MIDNA_DEBUG_QUEUE_GLOW=0.3` (holds the glow at that point for snapshots). The fake backend's `api` terminal has three queued messages and a Claude-style input box. Screens: `docs/screens/queue-*.png`. `queue-live-sent.png` is the real app against a temporary midnad, right after a resumed queue typed into a shell.
- **Tests.** `crates/midnad/tests/queue.rs` has 6 tests:
  - messages go in order and leave the queue;
  - the queue holds while the agent works and while it is paused, and an agent can queue into its own terminal;
  - edit, move, remove, clear and validation, plus the queue persisting on the session;
  - `at` holds the line and `send_now` skips the wait;
  - `after` waits for the other terminal;
  - a terminal whose process ended fails the message, raises a note, and can be retried.

  There are also CLI unit tests plus `queue_add_list_move_remove`, app unit tests (phrases, input-box detection, the model reading the wire type), and `local_triggers` passes with steps going through the queue.

## Background terminals (midna-proto `Session::background`, midnad `rpc/session.rs`, midna-app `ui/sidebar.rs` `background_group`; 2026-10-05)

- **A flag on the terminal, not a different kind.** `Session.background` (only serialized when true) is set by `session.open {background: true}` (`midna open --background`) or `session.set_background {id, background}` (`midna background <id> [--off]`, alias `bg`; ⌘K "Move X to background / foreground"). Changing it emits `session.background {background}`, but setting it to the value it already has emits nothing. Agents may call both. A background terminal is otherwise ordinary: it is in `session.list` (`midna list` marks it `(bg)`), readable and sendable, and it still raises needs-you items, because a failure nobody sees is worse than a little noise.
- **Sidebar.** Background terminals leave their project groups (`MainWindow::groups` skips them; a project with only background terminals drops out like a closed one) and sit in a **Background** group pinned between the project list and the footer, above a rule. It sits outside the list's scroll, so it never falls below the fold, and once unfolded its rows scroll on their own past 220 px. The heading is dimmed and shows a count, plus a needs-you dot when any of them needs you or failed. The group is **folded by default**. Unfolding it is remembered as `background_open` in `app-state.json`. Rows are drawn at 55% opacity, except the selected one. Clicking a row previews that terminal in the main pane like any other. A folded group keeps only the selected row, as folded projects do. Rows can be dragged to reorder within the group.
- **Navigation skips them while folded.** `ordered_sessions` puts background terminals last, and only while the group is unfolded (the selected one always). So ⌘]/⌘[, auto-select after a refresh and the close-neighbour choice don't land on a hidden terminal. ⌘K lists them all regardless.
- **Rail.** Shown dimmed after a rule, only while the group is unfolded (the selected one always).
- **Hiding the group.** Right-clicking the Background heading opens `Menu::Background` with "Hide from sidebar". This is the sidebar's first right-click menu. It opens upward, since the heading sits on the footer. Hidden (`background_hidden` in `app-state.json`) removes the group from the sidebar and the rail, even for the selected terminal. The terminals keep running, stay in ⌘K and still count in "N need you". A toast says how to undo it. ⌘K "Show background terminals in the sidebar" (`Run::Screen { screen: "background" }`) brings the group back and is always listed while it is hidden. Its "Hide…" counterpart is listed only when some terminal is in the background. Debug: `MIDNA_DEBUG_SCREEN=background-menu`.

## Subagents chip and read-only window (midnad `agent_work.rs`, `subagent_log.rs`; midna-app `ui/subagents.rs`, `ui/subagent_window.rs`; boards `docs/design/Subagents-B.dc.html`, `docs/design/SubagentWindow.dc.html`; 2026-10-05)

Canvas https://claude.ai/artifact/FuNu2MJ7p2k6RC1E88Dezf had A (a floating card in the terminal's top-right corner), B (a header chip with a popover) and C (live tiles). The user picked B, shown only while subagents run, with the orbit icon (they disliked the branching-nodes icon), and a click that opens a read-only window.

- **Descriptions.** `SubagentStart` carries only `agent_id` and `agent_type`. The description comes from the main thread's `PreToolUse(Agent)` (`tool_input.description`, plus `run_in_background`), kept in `AgentInfo.pending_agents` (not serialized). Each `SubagentStart` takes the oldest pending call of its type. `PostToolUse`/`PostToolUseFailure` with that `tool_use_id`, and a main-thread `Stop`, drop leftovers (a recorded worktree-isolation call failed with no hook at all). An async launch's `PostToolUse` names the agent (`agentId` + `description`) and corrects the match. Limit: two foreground agents of the same type launched together can swap descriptions. Claude's `subagents/agent-<id>.meta.json` has the exact `toolUseId`, but it is sometimes written minutes after the agent starts, so it isn't used.
- **Finished this turn.** A `SubagentStop` moves the agent to `AgentInfo.finished_subagents` with `ended_at` (at most 10, newest last; a woken background agent keeps only its latest run). The list is cleared by the human's next `UserPromptSubmit` and by a fresh start.
- **`session.subagent_log {id, agent, from}`** reads `<transcript without .jsonl>/subagents/agent-<id>.jsonl` from byte `from`, complete lines only, at most 4 MB per call. It returns `{agent, running, entries [{kind prompt|text|tool|result|error, text}], next, model}`. Tool calls show as `Name(description|command|file_path|pattern|…)`, and results as their first non-blank line plus "(+N lines)", skipping bare wrapper tags. Agent ids must be alphanumeric. It is read-only and in the MCP allowlist. CLI: `midna subagent <terminal> <agent>`; `midna procs` also lists finished subagents.
- **The chip** (`tb-subagents`, before the links button) shows only while something runs: live subagents, plus background ones waiting between wakes (those come from the Stop snapshot and have no start time). It stays while its popover is open, so it doesn't vanish under the pointer when the last agent finishes. It has the orbit icon, the count and a work-blue dot.
- **The popover** (`Menu::Subagents`, `keys.subagents` = ⌥⌘A) has two sections: Running (description, type, "background", elapsed) and Finished this turn (✓, duration). Keys: ↑↓ select, ↩ or a click opens, esc closes.
- **The window.** Subagents run inside the agent's process, so there is nothing to attach to. One window per subagent; opening it again brings it forward. It polls `session.subagent_log` every second while the subagent runs and stops when it's done. It shows:
  - the prompt in a box (4 lines, then "Show all");
  - `⏺ Tool(arg)`, `⎿ result` and error lines, the agent's text, and "✻ Working…";
  - in the header: running/done time and a read-only badge;
  - in the footer: the tool-use count and model, and "Show parent terminal", which selects the terminal in the main window it was opened from.
  New lines auto-scroll only while you're at the bottom.
- **Dev.** The fake backend's `api` terminal has three running subagents and one finished one, and serves a log. `MIDNA_SELECT=a1f00001 MIDNA_DEBUG_KEYS=cmd-alt-a` (add `,enter` and `MIDNA_SNAPSHOT_WINDOW=last` for the window). `MIDNA_SUBAGENT_LOG=<file> cargo test -p midnad real_subagent_log -- --ignored --nocapture` prints a real transcript as the window would.

## Open in IDE (midna-app `ide.rs`; settings `ide.app`, `ide.rules`; 2026-10-05)

- **Detection.** One `mdfind -attr kMDItemCFBundleIdentifier` query over the bundle ids in `ide::KNOWN` (Cursor, VS Code (+ Insiders), Windsurf, Kiro, Zed (+ Preview), Sublime Text, Nova, BBEdit, TextMate, the JetBrains IDEs, Android Studio, Xcode). Matching by bundle id finds renamed apps (e.g. `/Applications/VS Code.app`). Apps in the Trash or inside other bundles are skipped, and /Applications wins over ~/Applications, which wins over anywhere else. When Spotlight finds nothing for an editor, its usual names are looked up in /Applications, ~/Applications, ~/Applications/JetBrains Toolbox and /Applications/Setapp. Detection runs off the main thread at window creation and again each time the menu opens.
- **Icons.** The app's own `.icns` (`CFBundleIconFile`, else `CFBundleIconName`) is converted to a 64 px PNG with `sips` and cached in `~/Library/Caches/com.mrgnhnt.midna/ide-icons/`. It is redone when the app's Info.plist is newer. Apps with only an asset catalog fall back to the `code` icon.
- **Which IDE: `ide.rules`, then `ide.app`.** `ide.app` is the global default: `auto` (the first installed, in `KNOWN` order), an editor id, or an absolute path to any `.app` (which is added to the list). `ide.rules` (new `SettingKind::RuleList`: a JSON array of `match = value` strings, normalized; on the CLI, comma-separated) overrides it per folder. A match starting with `/` or `~` is a folder rule: it covers that folder and everything inside it, checked against the terminal's folder and its project, and the longest one wins. Any other match is a file rule: a `*`/`?` glob over the top-level file names of the folder and its project (`pubspec.yaml = android-studio`, `*.xcodeproj = xcode`), and the first one in list order wins. Folder rules beat file rules, which beat `ide.app`. Rules naming an editor that isn't installed are skipped. Both are normal settings, so agents can change them.
- **Header split button** (`tb-ide`, after the links button; hidden when no editor is found). The editor's icon opens the selected terminal's folder in the editor the rules pick (`keys.open_ide` = ⌥⌘E). The chevron opens `Menu::Ide` (`keys.choose_ide` = ⌥⇧⌘E): installed editors with icons and ✓ on the one that applies. The footer shows the folder, why that editor applies (chosen for this project / rule: pubspec.yaml / default IDE) and the key hints. ↑↓/↩/esc work.
- **Picking remembers per project.** ↩ or a click opens the folder there and saves a folder rule for the terminal's project (`~/path = id`, put first, replacing that project's old rule). If the other rules and the default would pick that editor anyway, the project's rule is removed instead, so the list stays short. ⌥↩ / ⌥-click sets `ide.app` and drops this project's rule. A terminal with no project always sets `ide.app`. The file-name listing is cached per folder and refreshed when the menu opens or ⌥⌘E runs.
- **Folder** = the terminal's `cwd` if it still exists, else its project's path. Opening runs `open -a <app> <folder>`, then toasts the result.
- **⌘K.** "Open in <IDE>" rows (`Run::OpenIde`, `CmdIcon::Ide`) for the selected terminal: the one the rules pick first with ⌥⌘E, then the others marked "remembered for this project".

## Resume after sleep (midnad `resume.rs`; settings `agents.resume_after_sleep`, `agents.resume_after_sleep_prompt`; 2026-10-05)
- **On by default.** A wake (wall clock jumped > 60s past the monotonic clock, same test as webhook reconciliation) puts every live agent terminal that was mid-turn on a 30-minute watch: status `working` or a turn open, or `failed` since the moment it slept.
- **Only a turn that died is resumed.** Claude reports a turn lost to a dropped connection as `StopFailure` (status `failed`, process still running). A watched agent in that state gets `agents.resume_after_sleep_prompt` (`continue`) through the queue (`by` = system, name "resume after sleep"), so it waits for the agent to be ready and never lands on a draft. It goes in 5s after the failure; if the turn fails again, 60s, then 300s, 3 tries in all. An agent that finishes by itself, exits or closes is dropped from the watch. Codex reports no `StopFailure`, so in practice this is Claude.
- **Queue fix.** `queue::readiness` treated every `failed` terminal as gone; a failed agent whose process is still running now takes queued messages.

## Resume after network loss (midnad `resume.rs`; setting `agents.resume_after_network`; 2026-10-06)
- **On by default.** A `StopFailure` whose `error`/`error_details` reads like a lost connection (`connection`, `network`, `timed out`, `fetch failed`, `ENOTFOUND`, `ECONNRESET`, …) puts that agent on a 6-hour watch, no sleep needed. Rate limits, auth and billing errors are left alone.
- **Waits for the network.** Typing `continue` while offline only fails the turn again, so a failed watched agent (from either watch, sleep included) gets its prompt only once a TCP connect to `api.anthropic.com:443` succeeds (checked at most every 5s, 3s timeout). Then the same queue path, prompt (`agents.resume_after_sleep_prompt`), backoff and 3 tries as resume after sleep, with `by` name "resume after network loss". Turning either setting off drops only its own watches.

## Open in Midna from Finder (midna-app `finder.rs`, `packaging/finder-sync`; setting `finder.quick_action`; 2026-10-05, extension 2026-10-06)

- **A Finder Sync extension, because only it gets an icon.** "Open in Midna" sits on Finder's right-click menu with Midna's icon, under Quick Actions. The 2026-10-05 version was a Quick Action workflow in `~/Library/Services`; tried while moving off it (2026-10-06):
  - Finder draws no icon for anything under Services (the plain list at the bottom), whether a workflow or a service declared in an app's Info.plist. AppKit attaches the provider app's icon to some app services (Terminal's "New Terminal at Folder"), but Finder drops it.
  - A workflow can have an icon only inside the Quick Actions submenu, and only saved as Automator saves one (`NSIconName` = `workflowCustomImage`, `Contents/Resources/workflowCustomImage.png`). A path, another name or an SF Symbol in `NSIconName` shows a blank page.
  - A Finder Sync extension's `NSMenuItem.image` is drawn, and its item sits in that bottom block, just under Quick Actions. Ad-hoc signed works too.
- **The extension** (`FinderSync.swift`, compiled by `build-app.sh` with `swiftc` into `Contents/PlugIns/MidnaFinderSync.appex`, id `<bundle id>.finder-sync`, signed with only the sandbox entitlement before the app). Watches `/`, so it's offered everywhere; menus for selected items and for a window's background (the folder shown). Title "Open in <name>" from its own `CFBundleDisplayName` (the sandbox can't read the app's), so Midna Dev's says "Open in Midna Dev". Icon: the app's, from `NSWorkspace.icon(forFile:)`.
- **Paths go as a URL, not file URLs.** The sandbox won't give another app file URLs ("does not have permission to open"), so each item goes as `<bundle id>://open?path=<path>`, opened with `NSWorkspace.open(_:withApplicationAt:)` on the app the extension ships in. The app registers its bundle id as a URL scheme (`CFBundleURLTypes`), so each flavor gets its own. `finder::folder_of` takes `file://` URLs and these (scheme must start with `com.mrgnhnt.midna`).
- **`finder.quick_action`** (Bool, default on; name kept for old settings). The main window calls `finder::sync` on every settings change; it acts only when the value changes: `pluginkit -a <appex>` (register a freshly installed bundle), then `pluginkit -e use|ignore -i <bundle id>.finder-sync`, the same switch as System Settings › Login Items & Extensions › Finder. Installed builds only; fake-backend builds skip it. The real app (not dev builds) also removes the old workflow if it carries midna's marker line, then `pbs -update`.
- **The app** takes the folders through `Application::on_open_urls`. They go through a channel, because a cold launch delivers them before the windows exist. Info.plist declares `public.folder` (`LSHandlerRank` Alternate, so Midna never becomes the default folder opener), which also lets you drop folders on the Dock icon. A file URL opens its parent folder. Each folder: a shell terminal whose cwd is that folder is shown (in whichever window has it). Otherwise `session.open {kind: shell, cwd}` opens a new one in the active main window, in the project containing the folder or a new project for it. Logged as `open folder: …` in `app.log`.

## Pasted secrets (midna-proto `secrets.rs`; midnad `rpc/secret.rs`; midna-cli `secret.rs`; midna-app `terminal/secret_paste.rs`; 2026-10-05)
Anything typed into Claude Code or Codex goes to the model. So a secret pasted into an agent terminal is stored locally, and the agent gets a name it can use but never a value. Two other ideas were dropped (the user decided they weren't needed): masking stored values in scrollback reads, and a `UserPromptSubmit` hook that blocks prompts containing a secret.
- **Detection** (`midna_proto::secrets::scan`, shared by the app and later the hook). Known prefixes (Anthropic/OpenAI, Stripe, GitHub, GitLab, Bitbucket/Atlassian, Slack, AWS, Google, npm, PyPI, Hugging Face, …), PEM private keys, JWTs, and `KEY=value` (dotenv lines, `export`, or inline in a sentence) whose key names a secret (`KEY`, `SECRET`, `TOKEN`, `PASSWORD`, …). The value is named after the key, and placeholders and `${VAR}` are skipped. A last-resort "Possible secret" catches a word of 24+ characters with upper case, lower case and digits, entropy ≥ 4 bits/char and no long letter runs; git hashes, UUIDs, paths and URLs don't count.
- **The sheet.** ⌘V into an agent terminal (an agent session, or Claude/Codex detected in a shell) scans first. If it finds anything, a card over the pane lists each value masked (`ghp_••••••hJ6`) with an editable name (a duplicate gets `_2`), a checkbox per value when there are several, and "Only this project". ↩ / ⌘↩ = Store and paste reference: `secret.set` for each, then the paste with `[secret:NAME]` in place of each value. "Paste anyway" sends the original; esc / Cancel sends nothing. ⌥⌘V (Paste as Secret, also in the right-click menu) opens it in any terminal; when nothing is detected, the whole clipboard is the secret. The Kass composer's send goes through the same sheet and then sends with ↩, as the composer would.
- **Scope.** A secret belongs to the terminal's project (root terminals: global), or to every project when the box is unchecked. A name resolves in the project first, then globally. The project comes from the caller's terminal, else from the deepest project folder containing the CLI's `cwd`.
- **Agents save secrets too.** A token a command produced (`gh auth token`, an API that issues keys) is piped in: `<cmd> | midna secret save NAME [--label L] [--global]`. The value comes from stdin only (an argument would land in the transcript and `ps`); one trailing newline is dropped; a TTY or empty stdin is refused; 64 KB max. The CLI sends `piped: true`. A value an agent passes itself (MCP `secret_set`, `midna call`) has already been in its context, so it's stored with `exposed: true` for the human to rotate. `added_by` records the agent (absent = the human). An agent's secret belongs to its terminal's project (or the cwd's project) unless `--global`.
- **Replacing the human's secret asks first.** New names and agent-stored secrets are saved at once. Replacing one the human stored becomes an approval: the agent's value is parked in the vault as `p_<hex>` (never in state.json or the needs-you item), and the deferred call is `secret.replace {pending, name, project_id, label, exposed, added_by}` (human only, catalogued as internal). Approving moves the value into place; deny, dismiss or `daemon.reset` delete the parked value (`close_needs_you` → `secret::drop_pending`). The deferred guard fingerprints the human's secret (id + last update), so an approval never replaces a value that changed after the human was asked.
- **Methods.** `secret.list` (metadata; agents see their project's and the global ones), `secret.set` (see above), `secret.replace` (internal, above), `secret.remove` (human only; deferred like the others), `secret.write {name, path, key?}` (upserts `KEY=value` in a .env file, keeping `export`; bare when safe, else double-quoted with `\n`; a new file is 0600; records `written_to`), `secret.exec_env` (internal, see SECURITY.md). `used` and `last_used_at` count exec and write. `daemon.reset` deletes them all.
- **CLI.** `midna secret [list] [--all]` (BY column: human / agent, "(exposed)"), `save NAME` (stdin), `exec NAME[,…] [VAR=NAME] -- cmd…` (stdin inherited; stdout/stderr scrubbed to `‹NAME›`; exit code passed through, 128+signal), `write NAME FILE [--as KEY]`, `rm NAME`.
- **Agents learn it** from the system hint (one sentence on `[secret:NAME]`), SKILL.md ("Secrets the human pasted"), `midna capabilities` and `midna explain secrets`.
- **Why the CLI runs the command (not midnad).** The command keeps the agent's sandbox, environment, cwd, stdin and process tree. Running it in midnad wouldn't have been safer: the child holds the value either way, so neither stops a determined agent. The goal is keeping the value out of the context by accident.
- **Dev.** `MIDNA_DEBUG_TERM` has a `paste:TEXT` step (`\n` = newline): a ⌘V of TEXT without touching the pasteboard.

## Global agent hooks (midnad `global_hooks.rs`; midna-app `ui/hooks.rs`; CLI `midna hooks`; 2026-10-05)
Agents midna starts get its hooks per launch (`--settings`, `-c notify`). A `claude` or `codex` typed into a shell terminal got none, so its status wasn't real. Now midna's hooks can also go into the agents' global config, as an opt in that only the human can turn on. The user chose "both": the global install and the per-launch wiring are either/or for each agent.
- **Methods.** `hooks.status` (per agent: `not_installed | current | stale | unavailable | error`, `detail`, `per_session`), `hooks.preview {agents, uninstall}` (diff lines, read only), `hooks.install` / `hooks.uninstall {agents}` (human only). Event `hooks.changed`; midnad re-checks every 5 s, so editing a file by hand updates the status bar.
- **Either/or.** While an agent's global install is `current`, midna starts Claude with `hooks/claude-settings-base.json` (permissions and statusLine, no hooks) and Codex without `-c notify`. Otherwise it injects as before and sets `MIDNA_HOOKS_INJECTED=1`, and `midna hook … --global` exits at once. That covers the stale case, where both sets would otherwise fire.
- **No effect on other apps.**
  - Claude entries are `[ -n "$MIDNA_SESSION" ] && [ -x '<cli>' ] && exec '<cli>' hook claude --global || true`. Outside a midna terminal the binary never runs, and a deleted midna is skipped rather than failing the hook.
  - Codex allows only one `notify`, so midna's is `/bin/sh -c <script> midna-notify <previous argv…>`. The script reports to midna only inside a midna terminal, then `exec`s the previous notify with the same arguments. Uninstall restores it.
  - `midna hook` sends `policy.request` only if `agent.hook` succeeded. midnad drops a `MIDNA_SESSION` claim from a process that isn't really in that terminal (`bind_caller`), so a GUI app started from a midna terminal is never held up by midna's approvals.
- **Files.**
  - Writes are atomic. The original is kept once as `<file>.before-midna`.
  - JSON key order is kept (serde_json `preserve_order` in midnad). TOML formatting is kept (`toml_edit`).
  - A file that doesn't parse (e.g. JSONC comments) is never rewritten: status `error`.
  - The user's `statusLine` and own hooks are left alone.
  - The CLI path is `$MIDNA_HOME/bin/current/midna` when installed, so updates don't make the install stale.
  - Tests use `Config::for_home`, which points `claude_dir` / `codex_dir` inside the temp home and never at `~/.claude`.
- **Stale** = an entry runs another CLI path, an event is missing (e.g. a new midna adds one), or an entry differs from what this build writes.
- **Status bar.** No item if neither agent is set up. Otherwise:
  - accent "Install hooks" while not installed;
  - "● Hooks" when current;
  - amber "● Reinstall hooks" (tooltip says why) when stale or unreadable.
  Each opens a sheet with the exact diff and Install / Reinstall, or "Remove hooks…" when current. Hooks are deliberately not an onboarding step.
- **Settings ▸ Agents.** "Claude Code hooks" and "Codex hooks" rows read `hooks.status` (reloaded on `hooks.changed`), replacing the old "Installed / Not found" check of the per-launch file. States: "Global · current" (green), "Global · out of date" (amber, `detail` as the note), "Per terminal" (not installed: midna adds its hooks to the agents it starts), "Can't read <file>" (error), "<agent> not set up" (dim, no button). The Install… / Reinstall… / Remove… buttons don't write from Settings: they bring the main window forward and open the same sheet, so the diff is always shown first. The sheet acts on both agents. settings.json view shows `status.hooks.claude|codex`.

## Sound effects (midna-proto `notify::EFFECTS`; midna-app `sounds.rs`; midnad `notify::play`; 2026-10-05)
The user asked for Saggar-style sound effects that can be turned on, turned off and changed. Saggar has one tone per state change (needs you, finished, failed, ready, select = Pop), a master switch, volume, "Play sounds while using Saggar" and "Mute until relaunch". The user picked all four kinds of moments (agent state changes, their own actions, UI cues, agent-triggered) and chose to **merge them into the notification sounds** rather than add a separate `sounds.*` family.
- **One sound library, one setting shape.** A sound effect is a kind with `notify.sound.<kind>` + `notify.volume.<kind>` (times `notify.volume`) and no banner, so the same picker, import, preview and `midna settings set` work. Actions: `approved`, `denied`, `queue_sent`, `image_added`, `closed`. UI cues: `switched`, `command_bar`, `copied`. Key names must not collide with categories (tested). Every kind's default is a Twilight sound at volume 100 (see below).
- **Agent state changes** reuse the categories. A banner that's skipped because you're looking at that terminal now plays its sound in the app.
- **Switches.** `notify.sounds` (default on) silences everything, including banner sounds (midnad drops the sound in `style`). `notify.sounds_in_app` (default on) = Saggar's "Play sounds while using": off silences sounds while midna is the frontmost app (effects, skipped-banner sounds, and banners shown while frontmost), so you hear only what happens while you're elsewhere. ⌘K "Mute sounds" / "Turn sounds on" flips `notify.sounds`. There's no "mute until relaunch".
- **Where they fire** (app): `resolve` (approve/done/restart = approved, deny = denied), Rules' remove/keep, `session.queue` sent (home window only), annotate "Add to chat", the three close paths, `select_only` / `select_step` when the terminal changes (not programmatic selects such as after a close), ⌘K opening, the terminal's copy, ⌥⌘C and the link preview's Copy. `crate::sounds` keeps a main-thread copy of the settings (synced on every settings refresh) so any view can call `sounds::play(kind)`.
- **Agent-triggered**: `notify.play{sound, volume?, session?}` takes a kind or a sound name (macOS names in any case), emits `notify.sound` (`notify::Played`) for the home window to play, or `afplay`s it from midnad when no app is connected (same `notify.when_app_closed` + `system_allowed` gates as banners). ## Twilight sounds (midna-proto `notify::TWILIGHT`; midnad `notify_media::install_twilight`; `tools/twilight`; 2026-10-05)
The user didn't like Saggar's sounds (the macOS set) and asked for Midna sounds from Twilight Princess, distorted into our own. I didn't use game audio: it's Nintendo's, and a distorted copy is still theirs, so it can't ship. Instead `tools/twilight/synth.py` synthesizes original sounds in that style (glottal-pulse "gibberish" through moving vowel formants, filtered-noise breaths, in-tune additive tones, a small comb reverb). They went through nine rounds on the board https://claude.ai/artifact/CtUNecrPJPDagzym8RzxXS (numbered cards, "Before" to compare rounds).
- **What the user liked and didn't** (keep for future sounds): they liked voice chirps for agent moments (Hm, Nn-nn, Uh-oh), breaths and portals, warm low chords, and very soft ticks. They didn't like ring-mod shimmer and inharmonic FM bells ("off", "weird", "too ting-y", "too much bell"), voices for approvals (three tries), anything that cuts off (let notes decay fully, then fade the tail on a curve), or hard transients (a thump needs a ~25 ms rounded attack and must sit under the main sound).
- **The set** (names are setting values, no extension, so they never clash with imports): approval Portal, attention Call, failed Uh-oh, turn_done Strum (so "Agent finished" now has a sound), agent and from_trigger Hm, approved Rise, denied Nn-nn, queue_sent Whoosh, image_added Fwip, closed Close, switched Tick, command_bar Thump, copied Tick-tick. Off-by-default categories (requests, background, …) stay `none`. The user chose "default for every kind", which turned the UI cues on by default. Each file carries its own level (the user approved them at full volume), so every effect's default volume is 100.
- **Shipping.** The WAVs (836 KB) live in `crates/midnad/assets/sounds/twilight/` and are `include_bytes!`'d into midnad. `install_twilight` writes them to `MIDNA_HOME/notify/twilight/<Name>.wav` at every start and replaces any that differ, so a retuned sound reaches existing installs. `notify::sound_file` resolves macOS, then Twilight, then imported. The app (`crate::sounds`, Settings preview), afplay and the banner rendering all use those files. Twilight sounds are built in: `notify.remove` refuses them, `notify.play` takes them in any case, and `settings.set` accepts them.
- **Picker**: yours first, then a "TWILIGHT" heading, then "MACOS" (`NotifyMedia.set`: `twilight` | `macos` | empty; a daemon from before the set reports macOS sounds only as `builtin`). Picking a sound now previews it for sound effects too (it used to preview notification categories only).
- **Rebuilding**: six files rebuild exactly from the script, and seven only approximately (see tools/twilight/README.md). The shipped WAVs are the source of truth.

## `claude` / `codex` typed into a shell terminal run under midna (midnad `adopt.rs` + `src/shell/*`, midna-cli `shim.rs`, midna-proto `agent_cli.rs`)

Why: people type `claude` or `codex` into a shell instead of opening an agent terminal, and then get none of midna's agent features (status, hooks, update prompt, restart into the same conversation). The user picked "adopt in place" over replacing the tab, with two requirements: the human can't tell anything switched, and nothing else is affected (2026-10-05).

- **Shims.** `$MIDNA_HOME/shims/{claude,codex}` (from `src/shell/shim.sh`, written at daemon start) are first on PATH in shell terminals. In a midna terminal they exec `midna shim <agent> …`. Otherwise, or when the CLI is gone, they exec the binary an alias named (`MIDNA_SHIM_REAL`) or the next one on PATH. A user's own `claude()` function (the /handoff wrapper) still runs: its `command claude` reaches the shim.
- **Staying first on PATH.** Startup files often rebuild PATH (the user's `.zshrc` does). Each shell gets midna's startup file, which runs the user's own files as usual and then puts `$MIDNA_SHIMS` back in front:
  - **zsh:** `ZDOTDIR=$MIDNA_HOME/shell/zsh`. Its `.zshenv` restores the user's ZDOTDIR (`MIDNA_ZDOTDIR`, else unset) and sources their `.zshenv`; zsh then reads their other files. A `precmd` hook does the PATH fix.
  - **bash:** can't take an init file as a login shell, so `bash -l` launches as `bash --init-file $MIDNA_HOME/shell/bash/init.bash -i` with `MIDNA_BASH_LOGIN=1`. The file runs `/etc/profile` plus the first of `.bash_profile`/`.bash_login`/`.profile` (or `.bashrc` when not a login shell), then a `PROMPT_COMMAND` hook. Only the plain shell midna starts is changed; a command the user gave runs as given.
  - **fish:** `$MIDNA_HOME/shell/fish` goes first in `XDG_DATA_DIRS` (the original comes back from `MIDNA_XDG_DATA_DIRS`, else it's unset again). Its `vendor_conf.d/midna.fish` hooks `--on-variable PATH` and `fish_prompt`, because vendor files run before the user's `config.fish`.
- **Aliases and full paths.** Before each prompt, an alias whose first word is the agent binary by full or `~` path (`alias claude=~/.claude/local/claude`, Claude's old installer) is rewritten to `MIDNA_SHIM_REAL=<binary> <shim> <rest>`. The shim then runs exactly that binary and unsets the variable for the agent's children. zsh also aliases the binaries themselves (zsh alias names may contain `/`: every `whence -pa` hit and each alias target, as absolute and `~` paths), so a binary typed in full is covered. bash and fish can't name an alias or function with a `/`, so there a binary typed in full runs as typed. fish's `alias` makes a function (recognized by its `alias x=…` description) and gets the same rewrite. One zsh gotcha: a quoted subscript keeps its quotes in the key (`aliases["~/x"]`), so the key goes through a variable.
- **`midna shim`** finds the real binary, and runs it as typed (exec, no midna involvement) unless stdin/stdout are a tty and `session.adopt` returns a command. ## The caller's own agent arguments (`session.open {agent_args, resume}`; midnad `agent_args.rs`; 2026-10-05)

## Terminals name themselves (midnad `auto_name.rs`; settings `terminal.auto_name`, `terminal.auto_name_updates`; 2026-10-06)

Why: every agent tab was called `claude`. Using the whole prompt makes names too long, and asking a model for a summary costs a call. Both agents already write a few-word task summary into the terminal title (Claude `◑ Auto-rename tabs with summary`, Codex `⠧ ⠧ Fix the login bug | midna`), and midnad already tracks titles, so that is the default source, at no cost.

- **Sources, strongest first.** `agent`: the title with spinner glyphs removed (`title_text`), Codex's ` | <folder>` dropped, placeholders (`Claude Code`, the bare folder) ignored. `prompt`: the prompt shortened with no model: the first sentence (`.` ends one only before whitespace, so `auth.rs` stays whole) that keeps 2+ words after dropping filler (pronouns, helper verbs, "can you", "options", "okay", …); small words (`in`, `for`, …) kept only between kept words; it stops at a side clause (`without`, `so`, `because`, a comma or dash) once it has 2 words, and at 5 words. Files, paths, ids and numbers are always kept. Slash commands and short replies (`yes`, `do those`) give nothing. `context`: the git branch made readable (kind and user prefixes dropped, `-`/`_` to spaces, `ABC-123` kept), `main`/`master`/… ignored; else the worktree name; else, in `context` mode only, the folder. Names are capped at 40 chars, cut at a word.
- **Modes.** `agent` (default): agent → prompt → branch, agent terminals only. `prompt`: prompt → branch. `context`: branch/worktree/folder, for shells too (never monitors). `off`. A name from a source the current mode doesn't use counts as no name, so switching modes renames.
- **Never over a chosen name.** `Session.auto_name {name, source}` records what midna set. A terminal is renamed only while its name is its default (the agent's name, the command's basename) or equals `auto_name.name`. `session.rename` clears `auto_name`, so any rename by the human or an agent freezes it; renaming it back to its default re-enables it. No migration needed: existing terminals still named `claude` start following.
- **Updates.** A stronger source always replaces a weaker one. `follow` (default) lets a source replace its own earlier name (a new task, a new summary); `first` doesn't. Renames emit `session.renamed` with `auto: <source>`, actor `system`.
- **When.** Title changes (`on_title`), `UserPromptSubmit` and Codex's notify (first input message), git info changes, `session.open` (for folders outside git), and a change to either setting (`refresh_all`: branch, last prompt, title in that order).

## Floating badge, per-kind duration and color, kinds you add (`ui/badge.rs`, `rpc/notify.rs` kinds; 2026-10-06)

Why: macOS sets Temporary/Persistent banners per app, not per notification, so approvals vanished as fast as finished turns. The design (D3 on the floating-notifications canvas) is a badge in a corner of the screen that counts what needs you, with a capsule that springs out beside it.

- **Per kind:** `notify.stay.<kind>` (seconds on screen, 0 = until handled or dismissed; 0 for approval, attention, failed and requests, else 6) and `notify.color.<kind>` (a theme color `need|ok|err|work|accent|dim`, or `#rrggbb`). Both ride on `notify.posted` (`stay_secs`, `color`, and `label` for a kind you added); the in-app card and the notifications list use them.
- **Kinds you add** live in `State.notify_kinds` (key, label, description). Their per-kind settings are ordinary settings under the same keys as a built-in kind's (`notify.<key>`, `notify.sound.<key>`, …), typed by the pattern specs in `settings::custom_kind_spec`; `State::setting_spec` resolves them, so settings.get/set/list, `notify.set` overrides and the media "used by" list need no special cases. Removing a kind drops its settings and every terminal's override for it. Keys can't shadow a built-in kind, a sound effect or a global `notify.*` setting. Agents send as one with `notify.send{category}` (CLI `--kind`); a trigger's notify action takes `category` (CLI `--notify-kind`).
- **The badge window** is a GPUI `PopUp` (non-activating NSPanel: every Space, over full-screen apps), fixed size, transparent, anchored at its corner of the screen's visible frame. A 30 Hz timer (4 Hz while hidden) lets clicks through everywhere but the zones measured as they paint (badge, capsule, stack), orders the window in and out, and tells a drag (`start_window_move`, then snap to the nearest corner with the native frame animation and save `notify.badge.corner`) from a click (open the stack) by watching the mouse button. Snapping and placing go through `NSWindow` because GPUI can't move a window.
- **What it takes:** `notify.badge` `background` (default: while midna isn't the active app), `always`, `off`. While it takes notifications, every recorded one shows there instead of as a macOS banner, with the sound a banner would have had; the in-app card shows only when it doesn't. It counts the home window's needs-you items plus notifications of kinds that stay (until dismissed). A needs-you notification can arrive before the needs-you refresh: it's counted from the notification and kept for 3 s against a stale list.
- **Screen sharing:** `notify.badge.sharing` `hide` (default: the window is ordered out; what comes in is still counted, and its lines aren't replayed when sharing stops), `count` (the badge and its number only: no lines, the stack doesn't open) or `show`. When sharing starts, any capsule or open stack goes at once. macOS has no public "is the screen shared" call, so the badge polls the WindowServer's private `CGSIsScreenWatcherPresent` every 500 ms, looked up with `dlsym` so a macOS without it just never hides. `MIDNA_DEBUG_SHARING=1` fakes a share. Not verified against a real Zoom/Meet share yet. Only the badge follows this: in-app cards and macOS banners don't (macOS hides its own banners while sharing by default).
- **Nothing waiting:** the badge hides at a count of 0 by default. `notify.badge.idle` (off by default) keeps it out, showing 0, for people who want it as a fixed place to click; `notify.badge` `off`, the `background` rule and screen sharing still hide it.
- **Not done:** the badge's screen isn't remembered across launches (it starts on the main screen); clicking, hovering and dragging were only checked by reading the code, not by driving the mouse (the screenshots covered counts, capsules, fills, the stack, corners and custom kinds).
- **Several at once** (2026-10-09, canvas https://claude.ai/artifact/7qwwu8WCXxwUiTtFLu9Jh8, option 3A): a new notification used to replace the capsule beside the badge with a "+N", and the human never got to read the ones it cut short. Now a passing capsule that's cut short goes into the list as a held row for `BUMPED` (5) times its kind's time, counted on the badge, its tint draining in its row (placed by the clock; the list redraws every frame while one is there). The pointer on a row, or its card open, holds it. When its time runs out it slides away like a row you take off with ×, or just goes when the list is shut or the row is above what you're looking at. Kinds that stay and needs-you items were already in the list. A first try stacked the capsules beside the badge instead; the human wanted them in the list ("I want to see the notification be added to the list when I open the pill").
- **Coming in while the list is open** goes straight into the list rather than out as a capsule; a passing one is held for `BUMPED` times its time. `reflow` compares the rows with the last snapshot whenever they change (`recount`). At the top of the list (scroll 0), a new row opens its room over `ROW_OPEN` (the rows below move down) and a band of its color sweeps across it. Scrolled at all, the rows on screen don't move: the scroll grows by the new row's room and an "↑ N new" chip at the list's top edge counts them; clicking it glides to the top, and scrolling back to the top clears it. A row that goes from above what you're looking at takes its room off the scroll too. Room is counted as `ROW + GAP` a row, so an open card above throws it off a little.
- Dev: `MIDNA_DEBUG_BADGE_SCROLL=<px>` (with `MIDNA_DEBUG_BADGE=list`) opens the list scrolled that far, to see the chip.
- Dev: `MIDNA_DEBUG_BADGE=panel|menu` opens the stack or the menu once something is waiting.

## Crons tab and schedule editor (`ui/triggers/schedule.rs`, proto `cron::Schedule`; 2026-10-06)

Why: Claude's session crons (CronCreate) were only visible as a `scheduled` line in `midna show`, with no sign of whether one repeats or when it goes away, and midna's own schedule triggers could only say *when* (a cron), not *between which hours*, *from when* or *until when*. Picked from the canvas: D, two tabs over the Triggers list (`docs/design/Crons-D.dc.html`) and a schedule editor (`docs/design/ScheduleEditor.dc.html`).

- **Crons tab.** Every terminal's `AgentInfo.crons`, soonest first, each marked Once or Repeats, with its schedule in words (`cron::describe`: `Every 5 min, 1 PM–5 PM, weekdays`), next run, created and expires. Claude owns them, so they're read-only: Open terminal, Copy to a trigger…, and Ask Claude to cancel it (a queued message asking for `CronDelete`, so it never types over a turn). Claude's CronCreate takes only `cron`, `prompt` and `recurring`, so a start, end or window can't be set on one; copying it into a trigger is how you get those.
- **Created / expires.** The `Stop` snapshot (`session_crons`) has no times, so midnad stamps `AgentCron.created_at` from the `CronCreate` PostToolUse (`tool_response.id`) and keeps it across snapshots; `CronDelete` removes one at once. Claude deletes a recurring cron 7 days after making it (after a last run; `CLAUDE_CRON_LIFETIME_SECS`), so `expires_at = created_at + 7d`; one-time crons end after their run. A cron that came back with a resume has no `created_at` and shows "7 days after Claude made it".
- **Schedule trigger fields** (local `schedule` triggers only; elsewhere they're refused): `filter.window {from, until}` (local `HH:MM`, from included, until not, `22:00`–`06:00` wraps midnight), `starts_at`, `ends_at` (RFC 3339) and `max_runs` (`1` = once; counts `fired`, and a changed limit resets `fired` to 0 so it counts from then). The window is its own field rather than folded into the cron's hours so `1:30`–`5:15` works. `cron::Schedule::of(filter, fired)` holds the whole rule; `local::due`, `trigger.test` and validation all go through it, as do the app and CLI ("never runs again" once it's past its end or out of runs). The Triggers list shows "ended" for those and the detail an Ended chip; they stay switched on.
- **Editor.** Runs Once (a date and time → a pinned cron + `starts_at` + `max_runs: 1`) or Repeats (every N minutes or hours, or daily at a time; a Between window; day buttons; Starts; Ends never / on a date / after N runs). A cron the form can't show stays as a custom cron field. Copying a Claude cron reads it into the form (`*/5 13-16 * * 1-5` → every 5 minutes, 13:00–17:00, weekdays) and sends the same prompt to the same terminal (`send_to_session`). Editing an existing trigger changes only its schedule and name. The summary under the form shows the rule in words, the next three runs and the cron it saves. This is the one place a trigger is made by a form rather than by asking: picking hours and dates is easier to do than to say.
- **CLI.** `midna triggers add|update --between 13:00-17:00 --starts '2026-10-06 13:00' --ends 2026-10-31 --max-runs N` (empty clears); `triggers show` prints the rule in words; `midna show`'s `scheduled` line adds the words and the expiry.
- Dev: `MIDNA_DEBUG_TRIGGERS_TAB=crons`, `MIDNA_DEBUG_TRIGGERS="new-schedule|edit:<id>|copy-cron:<n>"`; the fake backend's `api` terminal has three crons.

## Closing a terminal slides the list and the pane together (`ui/close_anim.rs`; 2026-10-06)

- **Picked C "Conveyor"** from three concepts (A fold, B power off, C conveyor) on the tab close canvas (https://claude.ai/artifact/9KAS8NqNU6TCduxbQhjLMq).
- **The row**: ⌘W keeps the closed row as a ghost for 320 ms (ease-out). Its content lifts 14 px and fades over the first 220 ms while its height folds to nothing, so the rows below slide up. The ghost takes no clicks.
- **The highlight** follows the terminal shown next (`neighbour`: up first, within the project):
  - the row right below: the ghost keeps the highlight where it was and the row slides up into it;
  - the row right above: the highlight glides up to it;
  - anywhere else, or several rows closed at once: it just moves.
- **The pane**: when the next terminal is promoted (after its first frame, as before), the closed one slides out the way the list moves (up when the next is below, down when it's above) and the next slides in behind it, in step, over 320 ms. If the next terminal takes longer than 1 s to draw, it just appears.
- Only ⌘W animates, including a multi-selection. A terminal that exits or is closed elsewhere just leaves. Rows in folded projects don't animate. With Reduce Motion on, nothing moves.
- **Opening runs it in reverse** (anything the sidebar's `open_session` opens: ⌘T, a new agent, the project menu). The new row unfolds over 320 ms while its content drops 14 px into place and fades up over the first 220 ms, and the rows below slide down.
  - It landed right below the terminal shown before (the usual case, new rows go last in their project): the highlight slides down to it, the reverse of closing with the next row above.
  - Right above: the highlight stays put and the new row unfolds into it as the old one slides down.
  - Anywhere else: the highlight fills the new row's room, solid, as it opens.
  - A project's run of rows clips only while it folds, so the highlight sliding out of the row above isn't cut off at that row's edge.
  - The pane slides the old terminal out and the new one in, the way the list moves, starting at once: the new terminal is shown and focused straight away, as before, so keys typed right after ⌘T reach it, and it may draw its first frame mid-slide.
  - Terminals opened from outside the window (`midna open`, another window) just appear.
- **Moving between terminals** with ⌥⌘↑ / ⌥⌘↓ (`select_step`) slides the same way (`switch`). The highlight glides to the next row over 320 ms, into and out of projects too (past the heading) and around the ends, from where each row was last laid out (`CloseAnim::rows`), growing or shrinking to the new row's height. The upper of the two rows draws it on its way, so the rows and headings below draw over it. A row in a folded project: it just moves. The pane slides the way the list moves (down the list: up), once the next terminal has drawn, as when closing. Clicking a row doesn't animate.

## Trigger commands in the Background group or with no terminal (issue #4; `midnad/src/headless.rs`; 2026-10-07)

- `run_command` takes `background` (the monitor terminal opens in the sidebar's folded Background group, through `session.open`'s existing `background`) or `headless` (no terminal). They don't mix, and `timeout_secs` is refused without `headless`. CLI: `--run CMD --background` / `--headless [--timeout 30m]`; on `triggers update` either alone changes the current command, and `--run CMD` alone makes it a tab again.
- **Headless results live on the delivery**, not a new store: `Delivery.command_runs` (one per headless trigger that fired for it), filled in by the run's own thread when it ends, so the trigger thread never waits. `triggers deliveries` appends `(exit 0)` / `(timed out)` to the outcome, `deliveries` detail and the app's firing rows show the same.
- Runs aren't adopted across a daemon restart or upgrade: the output pipe goes with the old process, so they're marked lost rather than left "running" forever.

## notify.send: a URL to open, buttons that report back, an id to replace or withdraw (GitHub #3, #5, #6; 2026-10-07)

- **Why**: the PR review log and the task board used terminal-notifier for `-open`, `-action` and `-group`/`-remove`, which kept those notifications out of midna's settings, kinds and history. `notify.send` now covers all three, from any process (it never needed a terminal).
- **`open`** (CLI `--open`, trigger `notify` action `open`, CLI `--notify-open`): any `scheme:` URL. A click opens it with `/usr/bin/open` instead of selecting a terminal, in every place a notification shows: the macOS banner (URL in `userInfo`), the in-app card (its Go button becomes Open), the floating badge's card and capsule, and the Notifications screen (an Open button). A webhook trigger's notification opens what the webhook is about (`url` fact) unless `open` says otherwise.
- **`id`** (`--id`, 1–64 of `A-Z a-z 0-9 . _ : -`; made up as `n-…` when left out, and returned): the banner's request identifier is `id:<id>`, so macOS replaces it; the in-app card and the badge drop the one with that id. `notify.history` (and the unread count) keeps only the newest per id. `notify.withdraw{id}` emits `notify.withdrawn`; the app removes the banner, card and badge entry, and the history item is marked `withdrawn` and stops counting as unread. Trigger `notify` actions take an `id` too (templates work).
- **`actions`** (`--action`, up to 6, 1–24 chars, no duplicates; was 4 and 40 before split buttons, below): a `UNNotificationCategory` per set of labels (registered on first use, at most 64 kept), action identifiers `action:<label>`. Every `notify.send` notification gets a category with `CustomDismissAction`, so a dismissal is reported too. In-app cards and badge cards show the labels as buttons; a notification with buttons stays until handled (`toast::stay_of`).
- **Responses**: the app reports a button, click or dismissal with `notify.respond` (human-only, internal). midnad keeps the last 500 `notify.send` notifications in memory (`notify::Sent`); the first response counts, emits `notify.responded {id, kind, action?, category, title}`, and wakes `notify.send{wait_secs}` / `notify.response{id, wait_secs}` (≤ 600 s; CLI `--wait 10m` prints the label, `clicked`, `dismissed` or `no response`). A local trigger on `notify.responded` is the "webhook" path. Responses don't survive a midnad restart.
- **No app running** (`via: system`): midnad's osascript banner can't carry a URL or buttons; the result's `via` says so.

- **Dev**: `MIDNA_DEBUG_PEEK=<project id>:<color>[,<project id>…]` folds the listed projects and shows the first one's card (colors: `needs-you`, `failed`, `working`, `finished`, `idle`). With the fake backend and `MIDNA_SNAPSHOT`, run from a scratch folder holding an `app-state.json` with `{"onboarding":{"finished":true}}`, or setup covers the window.

## Awake time: a night asleep isn't idle time (midnad `clock.rs`; RPC `clock.sleeps`; 2026-10-08)

- **The problem.** "How long since anyone touched it" checks done on the wall clock count the hours the Mac slept, so after a night asleep they all came due at once on wake: every `idle_minutes` trigger fired, `idle_for` queued messages went in, needs-you items and approvals were withdrawn as "nobody answered it in Nh" before anyone could see them, and a queued restart's `agents.restart_idle_secs` grace was already over.
- **Sleep log.** `Instant` stops while the Mac sleeps and the wall clock doesn't; a wall clock more than 60s ahead of the monotonic one since the last look is a sleep. `clock.rs` looks every second (and before each awake-time question, so a check that runs first on wake still sees the sleep), keeps the sleeps of the last 14 days in `$MIDNA_HOME/sleeps.json` (a daemon restart doesn't forget last night) and answers `awake_secs_since(unix)`. The wake detection moved here from `resume.rs`, which is told on wake as before; resume's watch windows were already `Instant`-based (awake time).
- **Awake time:** idle triggers (`idle_secs`/`idle_minutes` in their data are awake too), `idle_for` queued messages, `needs_you.expire_hours`, `agents.restart_idle_secs`. **Wall clock, on purpose:** `SendWhen::At` and schedules (real clock times), event-log retention and insights (calendar periods).
- **`clock.sleeps{since?}`** returns `{sleeps: [{from, to, secs}]}`, oldest first, so a client (Taskboard) can measure in awake time from midna's log instead of running its own detector. A wall clock set forward by hand reads as a sleep, accepted.

## Keep-awake: hold the Mac awake for agents during work hours (midnad `keep_awake.rs`, proto `keep_awake.rs`; 2026-10-08)

- **The problem.** The Mac idle-sleeps after a minute. Claude Code runs `caffeinate -i` only during a turn, so queued messages, `--at` and `--idle` sends, schedule triggers, wakeups and `agents.resume_after_sleep` all stalled once the human stepped away.
- **The mechanism.** midnad holds an IOKit `PreventUserIdleSystemSleep` assertion named "midna: keeping awake for agents" (visible in `pmset -g assertions`). No root, no `pmset disablesleep`: only idle system sleep is stopped; the display sleeps, the screen locks and closing the lid sleeps. The assertion belongs to the process, so it can't outlive midnad; it is released by hand before an upgrade's execv (and not retaken while `upgrading`), and the new image's first tick takes it again. A daemon inside another process (tests) never calls IOKit.
- **When.** A 5 s tick decides and takes or releases to match: off unless `keep_awake.enabled` (default off: changing how the Mac sleeps is opt-in); inside `keep_awake.start`–`end` on `keep_awake.days` (default 9 AM–6 PM weekdays; end ≤ start runs past midnight, equal = all day), with per-day `keep_awake.hours` rules (`fri = 09:00-15:00`, `sat = off`, `sun = all day`) that win over days. Mode `with_work` (default, energy first) holds only while there is work: an agent working or with background tasks or running subagents, an agent cron wakeup or a local schedule trigger or an unpaused queued message due before the hours end (24 h when they never end), or an agent `resume.rs` is watching; then `keep_awake.linger_mins` (default 5) after, so the next hook or queued message still finds it awake. Agents waiting on the human aren't work, nor are idle triggers or webhook triggers: mode `always` is for webhooks.
- **Battery.** On battery below `keep_awake.min_battery` (default 20%) it is released, and comes back only at +5 points (`BATTERY_HYSTERESIS`) or on AC. Read from `IOPSCopyPowerSourcesInfo` every 30 s; a Mac without a battery is never low.
- **Today.** One override in `state.json` (`keep_awake_today {date, on, until?, until_date?}`), not a setting: it belongs to a date, so it stops applying at local midnight and is dropped on the next tick. Off is off for the rest of today. On until a time is on until then and the schedule after (not off after: an expired "on until 3 AM" sat in status as "Not keeping awake: on until 3 AM today" until midnight), and the override is dropped when the time comes. The time may be past midnight (`for 5h` at 8 PM, `until 1am`, a time already past today is tomorrow's; 24 hours at most), recorded as `until_date`. Setting it needs keep-awake enabled.
- **Shape.** Mirrors Taskboard's work hours (`{on, start, end, days}` + today until) and its forgiving parsing (`8am`, `08:00`, `noon`; `weekdays`, `mon-fri`, `fri-mon`), stored as HH:MM and shown 12-hour. `keep_awake.set` takes any subset (`on` aliases `enabled`), checks every field before saving any, merges an `hours` object by day, and returns `keep_awake.status`; the keys are also plain settings. `keep_awake.changed` fires on held/reason changes and on every set.
- **Settings UI** (`settings_awake.rs`, 2026-10-08; canvas https://claude.ai/artifact/FftsYZafiRSYiSgqmLP34B, option C): one Hours row, a 24-hour track with a handle per end and a draggable bar (15-minute steps; an end before the start draws two stretches and runs past midnight; a midnight end sits at the right edge), saved once on drop through `keep_awake.set {start, end}`; the days are seven buttons (the last one on can't be turned off). Per-day `keep_awake.hours` is CLI-only ("we don't need days with their own hours in the UI"); the typed text fields are gone, which also ends the "didn't press ↩, so it wasn't saved" trap. No help line or Today row under the track (the user cut both); Off for today stays on the Now row.
- **Older daemon.** A setting the app knows but `settings.list` doesn't return means midnad is older than the app (it upgrades in place only when the app launches). The row shows "Needs a newer midnad" instead of a control (a control there would fail and snap back to the default: the "settings keep reverting" report), keep-awake's Now row and Settings › System › Daemon version explain it with an **Update daemon** button (`lifecycle::Cmd::UpgradeDaemon`, the launch-time `ensure_daemon_current`), and a failed change whose error is an unknown setting or method says the daemon needs an update. An upgrade failure is kept in the lifecycle snapshot and shown on the version row.

## Wake the Mac for scheduled work (midnad `wake.rs`; setting `keep_awake.wake`, RPC `keep_awake.wake_setup`; 2026-10-08)

- **The problem.** Keep-awake only stops idle sleep, so a 7 AM schedule trigger never ran on a Mac that idle-slept at midnight: the human wanted work to start before they sit down, lid open, screen locked.
- **What it wakes for.** The next work due inside the keep-awake hours (today's override included) within 8 days: a live schedule trigger, the head of an unpaused queue sent `--at` a time, an agent's cron wakeup. A run outside the hours skips ahead to when they open (`first_open`), so an hourly trigger wakes the Mac once, as the hours open, not all night. The wake is 2 minutes (`LEAD`) before it, in whole minutes; none on low battery.
- **Holding until it runs.** Within `LEAD` + 60 s of that work, keep-awake decides as if the hours were open (reason work), so a 7:00 trigger with hours starting 7:00 still finds the Mac awake at 6:58–7:00. Off by default; needs keep-awake on.
- **One wake, ours only.** midnad keeps exactly one macOS wake for the next work, cancelling ours that no longer match. The wakes carry the home's name as pmset's owner (`com.mrgnhnt.midna`, `com.mrgnhnt.midna.dev`), so `pmset -g sched` (no root) finds ours, Midna Dev's apart from Midna's; it is read again every 10 minutes (a reboot or `cancelall` may drop them). A failed call waits 60 s before trying again.
- **Root, once.** `pmset schedule wake` needs root (checked: "This operation must be run as root"), and a sudoers rule for pmset itself would be too wide (pmset takes more settings after `schedule`, `hibernatefile` among them). So `keep_awake.wake_setup` (human only) runs one admin script through `osascript … with administrator privileges` that installs a root-owned helper, `/Library/PrivilegedHelperTools/<home name>.wake`, taking exactly `wake|cancel 'MM/DD/YY HH:MM:SS'` (anything else exits 64 before pmset runs) with the owner baked in, and `/etc/sudoers.d/<home name, dots as dashes>-wake` (sudo skips names with dots) letting the user run only that helper without a password, checked with `visudo -c` before it goes in. The files are written from heredocs inside the admin script, never copied from files the user owns. midnad runs the helper with `sudo -n`, and checks the grant with `sudo -n -l` every minute. `remove` cancels ours, deletes both and turns the setting off. Only an app's home that owns its process gets this; temp and test homes say so.
- **The password dialog doesn't block.** It waits for the human longer than the app's 30 s call timeout, so it runs on its own thread; status shows `wake.asking`, the next keep-awake tick picks up the answer, turns `keep_awake.wake` on (off for remove) as the caller, and keeps an error ("cancelled: no administrator password given") in `wake.error`. `midna keep-awake wake setup` polls until it's answered (up to 5 minutes).
- **Status.** `keep_awake.status.wake {ready, asking, next?, reason?, line, error?}`; `keep_awake.changed` also fires when the scheduled wake moves. Settings › Agents › Keep the Mac awake has the row: a **Set up…** button until the grant is in, then the toggle with the line ("Waking the Mac tomorrow 6:58 AM for Morning kickoff at 7 AM").
- **Limits.** A closed lid keeps a laptop asleep (a wake in clamshell without a display goes back to sleep); the Mac must be on, not shut down.

## Runaway work: a busy Mac postpones upgrades, overload offers pause/stop, stale loops and worktrees go (midnad `guard.rs`, `worktrees.rs`, proto `system.rs`; 2026-10-09)

- **The incident.** A taskboard session ran 72 `isolation: worktree` subagents overnight. Each worktree had its own `target/`, so every agent cold-built the workspace (gpui included): ~20 rustc at once, load 79 on 12 cores, 36 worktrees holding ~290 GB. About 28 agent wait loops (`until ! pgrep -f "cargo test --workspace"; do sleep 5; done`) never ended: macOS pgrep skips its own ancestors, but each loop's command line has the pattern, so two of them keep each other alive forever (~1% CPU each for hours). Under that load the beta.14 auto-upgrade's new image didn't write `resumed` within the 10 s watchdog, was killed, and the fallback lost every terminal (launchd restarted the job and set the handoff aside).
- **Busy.** load1 per core ≥ `system.busy_load` (150%). `daemon.upgrade` / `daemon.restart` are refused while busy with error 7 (`BUSY`, data = `system.load`) and `daemon.upgrade_postponed`, unless `force`. SIGTERM restarts aren't gated (launchd is stopping us either way). Tests that spawn real daemons pin `MIDNA_DEBUG_LOAD=0`, since `cargo test` itself loads the Mac.
- **The window.** The app's `ensure_daemon_current` turns BUSY into a system window (`ui/system_window.rs`, a small window of its own): "Midna's update is waiting for a calmer moment", Wait (recommended) / Update anyway. Once per launch for the automatic upgrade; Settings' Update daemon asks again. The lifecycle thread retries every 60 s without force and closes the window when it goes through; Settings › System › Daemon version says it's waiting.
- **Watchdog.** `watchdog_secs` scales with load per core (10 s × load/cores, ≤ 60 s), and the watchdog keeps waiting past it while the new image's CPU time is still rising (it is resuming, slowly), up to 120 s. Not fixed: if the fallback does run under launchd, launchd may restart the job and `set_aside_stale` the handoff the fallback is resuming.
- **Overload.** Busy for `guard.overload_secs` (120) fires `system.overloaded` once per spell (a `SystemLoad` with the 5 terminals using the most CPU, from a 10 s sample of every descendant's CPU time) and `system.calm` below 80% of the bar. With `guard.overload_alert` the app shows the Overloaded system window: per terminal Pause / Resume (`session.pause|resume`: SIGSTOP/SIGCONT the whole tree, agent included, so nothing is lost and a resumed Claude carries on) and Stop processes (`session.stop_processes`: SIGTERM then SIGKILL after 3 s, everything under the terminal's own process; the agent keeps its conversation). Pause and stop are human only (agents get an approval); midnad never pauses or kills on its own for load.
- **Poll loops.** The one thing midnad stops by itself: under agent terminals only, a non-interactive shell (`-c`) whose script is a `while`/`until` loop around a `sleep`, older than `guard.loop_max_hours` (3; 0 = never). The agent and its shell stay. `procs.loop_stopped` says what went.
- **Worktrees.** Repos come from live terminals' folders and projects (`worktrees.json` remembers them). Every 10 min: `git worktree list`, then a worktree is removed with plain `git worktree remove` (never forced, so untracked files keep it; the branch stays) when idle `worktrees.auto_clean_hours` (24; last use = a terminal or any process's cwd in it, or its HEAD/index/reflog/dir mtime), no terminal or process is in it, `git status --untracked-files=no` is clean, and it isn't locked by a live pid. Claude Code locks an agent worktree as `claude agent <name> (pid N start …)` and leaves the lock when that process dies (the 10 left after the incident all named a dead pid), so a lock whose pid is gone doesn't count; a lock without a pid does. `worktrees.list` says why each is kept; `worktrees.clean {ignore_idle, path, dry_run}` runs it now.

## Cleaning up after a closed terminal (midnad `cleanup.rs`, proto `cleanup.rs`; 2026-10-09)

The human asked for this: when a terminal closes, a cheap headless model cleans up the workspace (local and remote branches, worktree). It can be turned on or off, the list can include or exclude anything, and users add their own items from the CLI and the UI.

- **Attribution, not guessing.** `git::refresh_session` calls `cleanup::observe` whenever a terminal's git info changes. That records the repo (main checkout), the branches its folder had checked out and the linked worktrees it was in. The first time a terminal goes into a repo, it also records the branches and worktrees that already existed. At close, the targets are the worktrees its folder was in, plus new worktrees that a process in its tree used or locked (Claude's `claude agent … (pid N)`). Branches are those worktrees' branches plus new branches it checked out, and remote branches are their upstreams. Nothing else is touched, so a branch that only appeared while it ran (another terminal's) stays.
- **Deterministic filters first.** Before the model runs, the plan drops `cleanup.keep` (globs for branches, absolute or `~/` paths for folders), the default branch (`origin/HEAD`), worktrees another live terminal is in, worktrees with any uncommitted or untracked file, and branches checked out in a worktree that isn't a target. `plan.skipped` says why for each.
- **The model does the judgment.** It decides whether something is merged, including squash merges through `gh pr view` (state MERGED and headRefOid equal to the branch tip), and it carries out the user's own items. It gets only read-only git and gh commands plus `git worktree remove|unlock|prune`, `git branch -d|-D`, `git fetch` and `git push --delete`, through `--allowedTools`, never `git push` in general. A dry run gets only the read-only ones. `cleanup.tools` (human only) adds tools for the user's own items. It runs as `claude -p --model <cleanup.model> --restricted --permission-mode dontAsk --strict-mcp-config --tools Bash Read Glob Grep --allowedTools …`, with the prompt on stdin. `--restricted` matters: without it the user's own settings apply, and on the human's Mac `defaultMode: bypassPermissions` let the test run delete a file with `rm`, which it was never allowed to use. The run goes in the repo's main checkout, in its own process group, without MIDNA_SESSION (so midna's hooks ignore it). It is stopped after `cleanup.timeout_secs`. Runs go one at a time per repo.
- **One list.** `cleanup.items` (a new `TextList` setting kind, split on newlines only so instructions can contain commas) holds the built-ins `worktree`, `branch` and `remote_branch`. Leaving one out turns it off. Every other line is the user's own item. The CLI edits it (`cleanup add|remove|enable|disable|keep|unkeep`).
- **When.** `session.close` (human or agent) and close-on-exit run it, unless `cleanup: false` (`midna close --no-cleanup`). `session.replace`, reset and removing a project don't. With `cleanup.sessions = agents` (the default), only agent terminals, including adopted ones, are cleaned up after. If there are no targets and no user items, nothing runs and nothing is spent.
- **Results.** The model ends with `REMOVED:` / `KEPT: … — why` lines, which are parsed into the run. Runs (the last 100) and trails live in `MIDNA_HOME/cleanup.json`, a run still going when midnad restarts is marked failed, events are `cleanup.started` and `cleanup.finished`, and the notification category `cleanup` (on, silent) says what went and what stayed. A dry run doesn't notify.
- **Overlap with `worktrees.rs`.** That module removes idle worktrees from any terminal after 24h. This one acts at close, on what that terminal touched, and also does branches.
- **UI** (canvas https://claude.ai/artifact/TzgiyN4nhvrRUw71jSsEt6, option A, `settings_cleanup.rs`). One group in Settings › Agents. `cleanup.items` is one list: built-ins have a switch and a BUILT IN tag, your own items have an ×, rows that are on can be dragged to reorder (saved on drop), and a field with Add (or ↩) sits under them. Built-ins that are off show dimmed at the end. `cleanup.keep` shows as chips with × and a field (commas add several). `cleanup.model` is a text field. Recent cleanups lists the last 5 runs: ✓ everything went, ● it kept something, ✕ failed. They refresh on `cleanup.started|finished`. To skip cleanup once, ⌥-click **Close terminal** in the header's More menu, or use the ⌘K row “Close terminal, keep everything”. The canvas's ⌥ on a close button became the menu item, because rows have no close button. The notification color stays one per category (no amber for kept).

## A notification card's like buttons fold into a split button (`ui/button_slots.rs`; 2026-10-09)

- **Why**: the floating badge's card laid `notify.send` buttons in one row that clipped, so with three snooze lengths and Open, Open was cut off and couldn't be reached. Design C ("split button + menu") on the notification-buttons canvas, with D's More as the overflow.
- **Grouping**: buttons are like when they share a group, ignoring case: the text before `": "` when the label has one (the sender grouping them on purpose: `Later: 1 hour`, `Later: tomorrow`), else the first word (`Snooze 15 min`). Two or more make a split button where the first of them was: its face is the first (one click, still the accent when it's the notification's first button), its caret opens a menu of all of them, named by what follows the group, or by full label when one would be blank (`Approve`, `Approve all`). It's only the look: a pick reports the full label, which is what midnad checks responses against.
- **Overflow**: at most 3 places in the row (`SLOTS`); past that the third becomes **More** with the rest, by full label. Open (or Terminal) is never in a menu: it goes somewhere rather than answering. The row also wraps as a last resort.
- **The menu opens inside the card**, under the row, and the card grows to fit (measured as it paints): the badge is its own small panel and a popover past its edge would be clipped. It closes with the card.
- **Limits**: up to 6 buttons (was 4), 24 characters each (was 40), so a face, its caret, More and Open fit a card's row.
- **Not changed**: the in-app toast already wraps its buttons and keeps one per label. The macOS banner is drawn by macOS, which puts buttons under Options.
